# 回答の再生成と取り消し

## Why

ユーザは bot の回答が気に入らないとき、同じ質問を投稿し直すしかなく、チャンネルに似た質問と回答が重なって残る。
不要になったやり取りを以後の会話から外す手段も、bot のメッセージを消せるモデレータにしか無い。
本 change は、同じ発言に答え直す**再生成**と、返答を会話から外す**取り消し**を加える。

## 依存 / 関連 change

- 先行（実装済み）: [conversation-context](https://github.com/AtefAndrus/disqord/blob/5f1bfa49759e1d5ee74e97718d61adff81f2b601/docs/changes/conversation-context/design.md) — 会話の本文は DB に保存せず、応答のたびに Discord から読む（`src/services/conversationWindow.ts`）。DB には返答の管理記録（`reply_records` と `reply_pages`、`src/db/schema.ts`）だけがあり、記録は発言 1 件につき 1 行で、発言の message ID が主キーである。本 change はこの記録の状態遷移と、窓に入れるかの判定（`src/services/messageEligibility.ts`）の上に載る
- 連携: [code-execution](../code-execution/design.md) — 実行結果のメッセージは回答と同じ生成に属する。再生成と取り消しでは、置き換えられる生成の実行結果メッセージを削除する。コンテナは生成ごとに採番されるので、再生成が前の生成のコンテナを引き継ぐことは無い
- 連携: [ギルド設定変更の共通認可](../permissions/design.md) — 再生成と取り消しの認可は「元の発言者本人または `ManageMessages`」であり、同 change の設定変更権限とは別の軸である
- 連携: [usage-stats](../usage-stats/design.md) — 再生成の usage と cost も計上対象である

## Goals / Non-Goals

**Goals:**

- 完了した返答を、同じ発言に対する新しい回答へ置き換える（再生成）。既存の返答ページを書き換え、新しい発言は作らない
- 返答を以後の会話の窓と `read_earlier_messages` から外す（取り消し）
- どちらも、元の発言者本人と `ManageMessages` を持つメンバーだけが実行できる

**Non-Goals:**

- 発言の編集を契機とした自動の答え直し。会話は応答のたびに Discord から読むので、編集後の本文は次の応答から文脈に入る。答え直しが欲しいときは、編集してから再生成を押せば、再生成が発言を読み直して編集後の本文で答える。編集のたびに自動で答え直すと、誤字の修正でも課金と返答の書き換えが起き、`messageUpdate` の購読と連続編集のまとめ処理も要るため採らない
- 取り消しの redo。返答の本文は Discord のメッセージにしか無く、取り消しでページを消すと戻す元が残らない。戻すために本文を DB に保存すると会話ストアを持つことになり、Discord を唯一の情報源にする前提と矛盾する。取り消した発言に答え直させたい場合は、発言し直す
- 世代の履歴と切り替え（前の回答に戻す、分岐ツリー）。前の回答の本文を保持しない
- 会話履歴の要約圧縮。窓の上限と縮小規則（`conversationWindow.ts` の `WINDOW_*` 定数）と、それより前をモデルが `read_earlier_messages` で取りに行く仕組みが、トークン量の上限を担う
- DM での操作。bot は DM の会話を扱わない

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| 再生成の表示 | 既存の返答ページを seq 順に `edit()` で書き換える。ページが増えれば追加送信し、減れば余りを削除する | チャンネルが再生成のたびに伸びない。返答ページは `channel.send()` で送られ（`messageCreate.ts`）、発言との対応は `reply_pages` にしか無いので、ページ ID を保ったまま書き換えれば対応づけも保たれる |
| 再生成中の記録の状態 | 生成の開始時に記録を `pending` へ戻し、終了時に再び確定する | `appendPage` は `pending` の記録にしか行を足さない（`replyRecord.ts`）。`pending` の間は窓の判定が返答ページを外す（`messageEligibility.ts` の `recordStatusReason`）ので、書き換え途中のページが他の応答の文脈に入らない |
| 再生成の確定時刻 | 確定しても `finalized_at` は初回確定の時刻のまま残す（**要判断**） | 窓の判定は、今回の発言の時刻以降に確定した返答を外す（`messageEligibility.ts` の `finalized-after-current`）。これは発言の時点で存在しなかった返答を見せないための規則である。再生成で `finalized_at` を新しくすると、元の返答から再生成までの間に投稿された発言の窓から、その時点で存在した返答が消える。記録の削除も `COALESCE(finalized_at, created_at)` から 24 時間で行う（`replyRecord.ts` の `deleteExpired`）ので、初回の時刻を保てば記録の寿命も変わらない |
| 再生成の対象 | そのチャンネルで最後に bot が答えた発言だけを対象にする（**要判断**） | 後に続く回答は元の返答を前提に書かれている。古い返答を差し替えると、後の回答が指す内容が会話から消える。対象を最後の返答に限れば、差し替えで前提が崩れる回答が無い。追加ページがチャンネルの末尾に離れて送られることも、後続の発言が少ない状況に限られる |
| 再生成の文脈 | 元の発言を Discord から取り直し、それを今回の発言として、ボタンを押した時点の窓の規則で窓を組み直す | 窓は今回の発言より前だけを読むので、元の発言より後のやり取りは入らない。発言の編集も反映される。ただし窓の縮小と経過時間の判定は現在時刻を基準にする（`conversationWindow.ts` の `build` は `now` を現在の時計から取る）ので、元の応答と同じ範囲は再現しない。古い発言の再生成では窓が縮み、空になることもある。対象を最後の返答に限るので、多くの場合は元の応答の直後に押され、差は小さい |
| 取り消しの方法 | bot が返答ページを削除し、`reply_records` と `reply_pages` の行は残す | 記録に登録されたページが見つからないと、窓の判定はそのやり取り（発言と返答）を外部削除として窓から外す（`messageEligibility.ts` の `classifyNotFoundMessage`）。削除だけで元の発言も文脈から外れ、スキーマの変更も要らない。ページを「取り消し済み」の表示へ書き換える方式は、書き換えた本文が返答として窓に入るので除外用の状態を別に足す必要があり、採らない |
| 取り消しの対象 | 記録が残っている返答すべて。生成中の返答は対象外（停止してから取り消す） | 取り消しはモデレータがページを消すのと同じ結果になり、後の回答への影響もそれと変わらない。生成中の取り消しを受けると、停止と削除とページ送信の順序を調停する必要が生じる |
| 操作の入口 | 返答の記録（`reply_records`）がある完了した返答の最終ページに、「再生成」と「取り消し」のボタンを付ける。`customId` には元の発言の ID を入れる | 生成中に付く停止ボタン（`stop_response_<発言 ID>`、`interactionCreate.ts`）と同じ形で、再起動後も記録から対象を引ける。3 秒以内に `deferUpdate()` で応答し、結果は bot トークンでのメッセージ編集で反映する |
| 対象にする guild | 会話履歴の設定が有効な guild だけ。無効な guild の返答にはボタンを付けない | 記録は履歴が有効なときにしか作られない（`src/bot/events/messageCreate.ts` の `createPending` と `appendPage` は `settings.historyEnabled` のときだけ動く）。履歴が無効なら返答は以後の文脈に入らないので、取り消しで文脈から外す意味も無い。履歴と独立に記録を作る案は、記録の 24 時間の TTL と窓の判定を履歴の無い guild にまで持ち込むので採らない |
| 認可 | 元の発言者本人（`interaction.user.id` が発言の author）か、`ManageMessages` を持つメンバー。満たさなければ ephemeral で断る | 共有チャンネルでは、ボタンは他人にも見えて押せる。他人の質問への回答を書き換えたり消したりできないようにする |
| 同時実行 | 再生成も取り消しも、Discord への書き込みの前に記録を `completed`、`stopped`、`failed` のいずれかから `pending` へ CAS で移し、成功した操作だけが進む。記録が `pending` のあいだの操作は断る。再生成の生成は `ChatService` の `activeRequests` に元の発言 ID で登録する | 同じ CAS を両方の操作が取るので、再生成中の取り消しや、同時に押された再生成は片方だけが進む。停止ボタンがそのまま再生成を止められる |

## Design

### 変更対象ファイル

- 修正: `src/db/repositories/replyRecord.ts` と `src/services/replyRecordService.ts` — 確定済みの記録を `pending` へ戻す CAS、`finalized_at` を変えない確定、チャンネル内で最後に答えた発言の判定
- 修正: `src/bot/events/messageCreate.ts` — 生成と描画の流れを、既存のページを受け取って書き換えられる形に切り出す
- 修正: `src/bot/events/interactionCreate.ts` — 「再生成」と「取り消し」のボタンの処理
- 修正: `src/utils/buttonBuilder.ts` と `src/utils/chatContainerBuilder.ts` — 完了した返答の最終ページへのボタン追加。`bun run preview` の対象にも加える

### DBスキーマ変更

表と列の追加は無い。
「チャンネル内で最後に答えた発言」の判定に `reply_records(channel_id)` の index を足すかは、記録が 24 時間で消えることを踏まえた件数から実装時に決める。
発言 ID の大小は snowflake の数値で比べる（TEXT の文字列比較は桁数が違うと誤る）。

### 再生成の流れ

1. ボタンの処理が `deferUpdate()` で応答し、`customId` の発言 ID で記録を引く。記録が無い（24 時間で削除済み）、`pending`、発言が削除済みのいずれかなら断る。
2. 認可と、対象がそのチャンネルで最後に答えた発言であることを確かめる。
3. 記録を `completed`、`stopped`、`failed` のいずれかから `pending` へ CAS で戻す。失敗したら、別の操作が先に進んだとして断る。
4. 元の発言を Discord から取り直し、それを今回の発言として窓を組み、`runToolLoop()` で生成する。停止ボタンのために `activeRequests` へ登録する。
5. 既存ページを seq 順に書き換え、足りなければ追加送信して `appendPage` し、余りは削除して `removePage` する。置き換えた生成の実行結果メッセージを削除する。
6. `finalized_at` を変えずに状態と `page_count` を確定する。生成が失敗したら `failed` で確定し、書き換え済みのページには失敗表示を出す。

起動時は `pending` の記録を `failed` にする（`markPendingFailed`）ので、再生成の途中で落ちた返答は窓から外れ、もう一度再生成できる。

### 取り消しの流れ

1. ボタンの処理が記録を引き、`pending` なら断る。認可を確かめる。
2. 記録を元の状態から `pending` へ CAS で移す。失敗したら、別の操作が先に進んだとして断る。
3. 返答ページと、その生成の実行結果メッセージを削除する。`removePage` は呼ばず、`reply_pages` の行を残す。
4. 記録を元の状態へ戻す。途中で落ちた場合は起動時に `failed` になり、ページは消えているのでどちらでも窓から外れる。
5. 押した本人にだけ ephemeral で結果を返す。

窓の判定は、登録されたページの取得が not-found になった時点でやり取りを外す。
取り消したやり取りが窓の範囲にあるあいだは、消えたページの取得に Discord REST を 1 回使う（応答ごとの上限は `CONVERSATION_REST_LIMIT`）。

## Tasks

- [ ] 「要判断」の 2 行（確定時刻、再生成の対象）を決め、`status` を `planned` にする
- [ ] 記録の CAS（`pending` へ戻す、`finalized_at` を変えない確定）と、チャンネル内で最後に答えた発言の判定を実装し、テストする
- [ ] `messageCreate.ts` の生成と描画を切り出し、既存ページの書き換えに使えるようにする
- [ ] ボタンと interaction の処理（認可、同時実行の拒否）を実装し、テストする
- [ ] 取り消し後の窓からやり取りが外れることを、窓のテストで確かめる
- [ ] ボタンは bot から押せないので、再生成と取り消しの動作は `手動確認` のタスクとして残す
- [ ] `docs/changes/conversation-regeneration/` 削除（リリース完了時、git 履歴がアーカイブ）

## Open Questions / Risks

- **確定時刻を保つ代償**: `finalized_at` を初回の時刻のまま残すと、元の返答から再生成までの間に投稿された発言の窓には、その発言の時点では無かった新しい回答が入る。再生成の対象を最後の返答に限れば該当する発言は少ないが、ゼロにはならない。`finalized_at` を更新する方式では、その間の発言の窓から返答が丸ごと消える。どちらの欠落を許すかを決める。
- **追加ページの位置**: 再生成で回答が長くなると、追加ページはチャンネルの末尾に送られ、元のページと離れる。対象を最後の返答に限っても、元の返答の後に人の発言があれば起きる。
- **取り消しを外部削除として扱うこと**: 判定上の理由は `externally-deleted` になり、ログでは人やモデレータによる削除と区別できない。区別が要るなら記録に状態を足すが、`status` の CHECK 制約を変えるには表の作り直しが要る。
- **ボタンの常設**: 完了したすべての返答に 2 つのボタンが付く。メッセージのコンテキストメニューを入口にする案は表示を増やさないが、見つけにくい。
