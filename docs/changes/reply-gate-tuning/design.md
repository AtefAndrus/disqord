# 自動応答の返答判定の見直し

## Why

自動応答チャンネルでは、メンションの無い発言に返答するかを判定モデル Jev（`typesafe/jev-1.14`）が決める。
返答するのは、返答すべき確率（`noul`）がしきい値 `REPLY_GATE_THRESHOLD`（既定 0.3）以上の発言である（`src/services/replyGateService.ts` の `judge`）。
2026-10-17 の本番のスレッドでは、21 件の判定がすべて返答になり、bot は人どうしの会話、独り言、bot への制止にも割り込んだ。

21 件を下の「本番の判定」の表のとおり分けると、返答すべき 9 件の `noul` はすべて 0.74 以上で、黙るべき 12 件のうち 9 件は 0.32〜0.48 に集まっている。
この分布から読み取れる原因は四つある。

1. しきい値が低い。表の値では、しきい値が 0.5 なら黙るべき 12 件のうち 9 件が黙り、返答すべき発言の取りこぼしは無い。0.5 以上に残る黙るべき発言は、0.50 ちょうどの 20 を含めて 3 件である。
2. 判定の問い（`buildReplyGateQuestion`）の黙る側の基準に、「bot に黙るよう求める発言」が無い。bot への制止は bot を「お前」と呼ぶので、返答する側の基準「bot に向けた発言」に当たる。黙る側には「bot の回答への礼や人どうしの反応」が既にあるが、bot の返答を受けて人どうしで話した 11 と 14 は 0.85 と 0.77 になった。返答する側の「bot の直前の回答への続きの質問」に寄せて読まれた可能性がある（推測）。
3. 返答を生成するモデルには、今回の発言が判定を通って選ばれたことも、自分が今後の返答を制御できないことも、専用の指示で伝えていない（`src/services/chatService.ts` の system 指示の組み立て）。この会話では、bot は独り言のメモにも依頼として答え、仕組み上守れない「今後は呼びかけられたときだけ返します」という約束もし、返答は「ほかの話題も気軽に投げてください」のような誘いで終わることが多かった。会話の冒頭で自動応答のテストだと書かれていたので、指示が無いことがこれらの原因だとは確かめられない。指示を足すことで減るかは仮説として扱う。
4. bot が毎回返答するので、新しい発言の直前は常に bot の返答になり、次の人の発言が bot への続きとして読まれやすくなる（推測。判定の状態の組み立てと問いの文面から）。原因 3 の誘いの言葉は、この傾向を強めている可能性がある。

このスレッドはテストのための会話で、最初の発言が bot の介入を促している。
話題の多くは bot 自体についてで、参加者は 2 人なので、21 件は普段の雑談より判定が難しい側に偏っている。

## 依存 / 関連 change

- 先行（実装済み）: reply-gate（v1.15.0）— 本 change はその判定の問い、状態、しきい値を見直す
- 先行（実装済み）: [author-identity](../author-identity/design.md) — 判定に渡す発言者の名前を `表示名 (@ユーザー名)` の形にした。名前の形が変わると `noul` も変わりうるので、しきい値と問いの測定はこの形で行う

## Goals / Non-Goals

**Goals:**

- bot について人どうしで話している発言、bot への制止、独り言に返答しないようにする
- 判定を通って返答するときに、bot が守れない約束をせず、返答を誘う言葉で締めないようにする
- しきい値と判定の問いを、手書きの例と本番から作った例の両方で組にして測り、決める

**Non-Goals:**

- メンションされた発言の扱い。今までどおり必ず返答する
- 判定を通さない自動応答（判定が無効、または無料モデルのみの guild）の挙動

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| しきい値 | 0.3、0.4、0.5 を下の「採否の基準」で比べて決め、`src/config/envVars.ts` の既定値を変える（`.env.example` は `scripts/generate-readme.ts` がそこから生成する） | しきい値は環境変数 1 つで戻せ、本番の分布では誤った返答の大半がしきい値だけで黙る。ただし、今の問いのままでは上げられない見込みである。手書きの 77 件を 3 回ずつ判定したとき、返答すべき例の 1 回ごとの判定の最小は、reply-gate の設計時（2026-10-18、コミット 4025139 の design）で 0.35、`表示名 (@ユーザー名)` の名前の形にした後（2026-10-18、author-identity の PR #228）で 0.38 だった。どちらも 0.4 を下回るので、0.4 以上は採否の基準 1 を満たさない。しきい値を上げられるかは、問いの変更でこの最小を上げられるかにかかっている。問いを変えずにしきい値だけを変える組も、候補として同じ基準で比べる |
| 判定の問いの黙る側の基準 | 「${botName} に黙る、口を挟まないよう求める発言（${botName} に向けていても黙る）」「${botName} に答えを求めず、${botName} の仕組みや挙動について人どうしで推測や感想を述べる発言」「独り言やメモ」を足す。${botName} の能力を直接問う疑問は返答する側に残す | 原因 2 に当たる。制止は bot に向けた発言の形をとるので、黙る側を優先すると明記しないと、1 つの問いの中で返答する側の基準と重なる。bot についての発言は、bot に答えを求めているか、人どうしで推測や感想を述べているかで分け、語尾（〜かな、〜かも、疑問形）は補助の手がかりとする。制止に返答しないことで、bot が「黙ります」と約束する場面自体が無くなる |
| 判定の問いの返答する側の基準 | 「${botName} の直前の回答への続きの質問」を「${botName} に答えや作業を求める、または ${botName} の回答への指摘、訂正、理解できないという反応を伝える、直前の回答への続き」に狭める候補を、上の変更と同じ評価で測る | 11 と 14 は黙る側に「人どうしの反応」があっても高く出たので、黙る側に文言を足すだけでは下がる根拠が無い |
| 判定を通った返答への指示 | 判定を通った発言（判定が失敗して返答に倒した場合を含む）への返答にだけ system 指示を足す。内容は、この発言は bot に向けたものではない可能性があること、返答を誘う問いかけで締めないこと、今後の返答のしかたを約束しないこと。会話履歴の有無にかかわらず付ける | 原因 3 と 4 に当たる。返答するかは判定が決めるので、モデルが約束しても守れない。返答の長さは指示しない。判定を通った発言には「一番古い発言を引用して」のような正当な依頼も含まれ、長さを縛るとその返答が損なわれる。メンションされた発言には足さない |
| 自動応答で返した印を判定に渡すこと | 判定の状態で、判定を通って返した bot の返答に「（自動応答）」の印を付ける案を、上の変更と同じ評価で測り、採否の基準の回数が減れば入れる。どの返答が判定を通ったかは、`ReplyGateService` が判定を通した発言の ID（判定が失敗して返答に倒した発言を含む）を、黙らせた発言と同じく 1 時間メモリに持って決める。1 時間より前の返答には印が付かないが、窓が扱う会話も 1 時間以内なので（`WINDOW_RAW_AGE_MS`）、影響は返信先として状態に入る古い返答に限られる | 原因 4 に当たる見込みがあるが、効果は測っていない。メンションの有無ではなく判定を通ったかで決めるのは、名前で呼ばれた発言（本番の 1）も判定を通るからで、印の意味は「呼ばれたか」ではなく「bot が自分の判断で返したか」とする。返答の記録（`reply_records`）に列を足す案は、再起動後も印が残るが、窓が扱うのは 1 時間以内の会話なのでスキーマ変更に見合わない |
| 自動応答を一時停止する tool | 採らない | 制止は判定の問いで黙らせるので、モデルに届かず tool が呼ばれない。届いた場合も、本番のスレッドでは 15 の制止の 22 秒後に別の参加者が bot に質問しており、1 件への叱責を一定時間の停止と読むと正当な返答まで消す |
| モデルに黙ることを選ばせる案 | 採らない | 「生成中...」を先に送るので、黙ると表示が出て消える。生成の費用は 1 件およそ $0.0009 で、判定（およそ $0.0001）の約 10 倍かかる（2026-10-17 の本番の値） |
| 判定を複数の問いに分けること | 本 change では行わない | Decisions API は 1 回の呼び出しで複数の問いを受け付ける（`https://openrouter.ai/openapi.json` の `/api/alpha/decisions` の例）。しかし、問いを組み合わせる規則と問いごとのしきい値を決める根拠が無く、問いが増えたときの費用と遅れも確かめていない。採否の基準を満たす組が無いときに検討する |
| 本番の判定を評価の例にすること | 下の表の 21 件を、言い換えた文面と表の正解で `scripts/reply-gate-cases.ts` に足す。足す前に、今の問いで、元の文面と言い換えた文面を同じ名前の形でそれぞれ 3 回判定し、`noul` の平均の差が 0.05 以内の例だけを使う。外れた例は言い換え直し、それでも外れる例は除く。元の文面の 21 件はコミットせず手元に残し、採否の基準で選んだ組を、新しい問いのもとで元の文面でも判定して確かめる（採否の基準 5） | 手書きの例には bot について話す例や独り言の例はあるが、bot の返答が密に並ぶ履歴、bot への制止、テストのための会話は無い。言い換えるのは利用者の発言をリポジトリに残さないためで、判定は語尾や「お前」「草」のような手がかりで値が動くので、言い換えで値が変わっていないかを確かめる。本番のログの値は 1 回だけの標本なので、比べる相手は元の文面を判定し直した値にする。今の問いで値が近くても、新しい問いのもとで言い換えの前後が同じに振る舞うとは限らないので、選んだ組は元の文面でも確かめる |

### 採否の基準

候補の組は、問いの文面、自動応答の印の有無、しきい値の 3 つの軸の組み合わせである。
文面と印の組み合わせごとに、手書きの例と本番の例を例ごとに 3 回判定する。
しきい値は `noul` を変えないので、しきい値ごとに判定し直さず、各例を 3 回判定した結果を共用して、0.3、0.4、0.5 のそれぞれを当てて数える。

手書きの例で印を付けるのは、bot の返答の直前の発言がメンション（`<@1>`）を含まない返答である。
手書きの例は bot を名前で呼ぶ書き方が多いので、ほとんどの返答に印が付く。
本番の例では、メンションされた 1 件目の前の返答を除くすべての返答に付ける。

判定は本番と同じく 3 秒で打ち切る（`REPLY_GATE_TIMEOUT_MS`）。
打ち切られた判定と、API がエラーを返した判定は、本番では返答に倒れるので「しきい値以上」として数える。
数値が得られなかった判定の件数と、判定の所要時間の中央値と 90 パーセンタイルは、組ごとに結果と並べて書く。

1. 返答すべき例（手書きと本番の両方）の判定が 1 回でもしきい値を下回る組は除く。
2. bot への制止の例（本番の 12、15、21）の判定が 1 回でもしきい値以上になる組は除く。
3. 本番の例の黙るべき件のうち、3 回ともしきい値を下回る件が「本番の黙るべき件数 − 3」に満たない組は除く。言い換えの確認で除いた例は、黙るべき件数にも数えない。ただし、制止の例と、11、14 のどれかを除いた場合は、どの組も採らずに言い換えをやり直す。
4. 残った組の中で、黙るべき例（手書きと本番の合計）の判定がしきい値以上になった回数が最も少ない組を採る。同数なら、しきい値の高い組を採る。それでも同数なら、印を付けない組、問いの変更が少ない組（今の問い、黙る側の基準だけを変えた問い、両側を変えた問いの順）を採る。自動応答の印は、同じ問いとしきい値で印を付けない組と比べて、この回数が減るときだけ入れる。
5. 選んだ組を、新しい問いのもとで元の文面の 21 件でも 3 回ずつ判定し、基準 1 から 3 を満たすことを確かめる。満たさなければ、その組は採らずに次の組を確かめる。
6. 残る組が無ければ、どの組も採らず、判定を複数の問いに分ける案を検討する。

過去の状態を固定して判定し直す評価では、bot が黙った後に次の発言の直前が人の発言になる効果は測れない。
原因 4 への効果は、リリース後の本番のログで見る。

### 正解の付け方

正解は、誰に向けた発言か、bot に答えや作業を求めているか、人の側で引き取る意思を示しているかで付ける。
語尾（〜かな、〜かも、疑問形）は補助の手がかりで、それだけでは決めない。

- bot に質問、依頼、指摘をしている発言は返答とする。
- bot について、または bot の返答を受けて人どうしで話している発言は、bot の名前や「お前」を含んでいても黙るとする。2 と 3 は bot の仕組みについての推測を場に述べたもので、bot に答えを求めていないので黙る。16 は bot の能力を bot に直接尋ねているので返答とする。
- bot に黙るよう求める発言と、独り言やメモは黙るとする。8 は「よく分からない」という反応を含むが、続けて自分で直すと述べており、人の側で引き取っているので黙る。
- 11、14、20 は、bot がそれに返答した直後に、発言した本人が 12、15、21 で bot を制止している。11、14、20 を黙るとする根拠である。
- 4 と 19 は、どちらも bot の返答への突っ込みで、上の規則だけでは決まらない。4 は bot の説明を受けて人どうしで笑っている発言として黙るとし、19 は bot の返答の矛盾を bot に指摘している発言として返答とする。この 2 件は運用の方針として付けた正解であり、19 の後に制止が無いことは、返答が望まれていた証拠ではない。

手書きの例には、語尾だけで判定していないかを見るために、bot に向けた「〜かな」の質問（返答）と、人に向けた直接の疑問（黙る）を対にして足す。

- e2e のテスト用 bot は必ずメンションするので、判定を通る経路は e2e で通らない。判定と system 指示の効果は、評価のスクリプトと手動確認で見る。
