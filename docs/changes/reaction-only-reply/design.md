# リアクションだけで応える返答

## Why

メンションされた発言と、自動応答の判定で返答すると決まった発言には、bot は今は必ず本文で返答する。
その中には「ありがとう」「了解」のように、bot に答えも作業も求めていない発言も含まれる。
人どうしの会話なら、こうした発言にはリアクションだけで応えることが多く、本文の返答は会話に割り込んだように見える。

今の仕組みでは、モデルがリアクションだけで済ませようとしても成立しない。
モデルが `add_reaction` を呼ぶと必ず次のモデル呼び出しが続き（`src/llm/toolLoop.ts` の tool 呼び出し後の `continue`）、その呼び出しが本文を返さないと、空の応答としてエラーになる（同ファイルの、`finish_reason` が `stop` で本文が空のときの処理）。
利用者には、リアクションに加えて、エラー ID 付きのエラー表示の返信が届く。

## 依存 / 関連 change

- 連携: [reply-gate-tuning](https://github.com/AtefAndrus/disqord/blob/ebb1c6b95ec976b3c76abf215cbdb167ccb23a2b/docs/changes/reply-gate-tuning/design.md)（v1.16.0 でリリース済み）— 自動応答の判定は、bot の回答への礼や相づちを黙る側に置いている。本 change は、判定を通った発言とメンションされた発言の中で、本文の要らないものを扱う
- 連携: [discord-expressions](../discord-expressions/design.md) — `reply_with_reaction` は `add_reaction` と同じ処理でカスタム絵文字を名前で引くので、そちらの変更がそのまま適用される

## Goals / Non-Goals

**Goals:**

- メンションされた発言と、自動応答の判定を通った発言に、モデルの判断でリアクションだけで応えられるようにする
- モデルが他の tool を呼ばずに待ち時間 T のうちにリアクションだけの返答を選んだときは、「生成中...」のメッセージを表示しない
- 次の返答で、モデルが自分のリアクションを他の人のリアクションと区別して読めるようにする

**Non-Goals:**

- 自動応答の判定で黙ると決まった発言にリアクションを付けること。判定はリアクションの絵文字を選べず、選ぶにはモデルの呼び出しが要るので、黙る判定で節約している費用が無くなる
- 定期実行、コンテキストメニュー（解説、LLM 入力の表示）など、チャンネルの発言への返答以外の経路
- 現在の発言以外の発言にリアクションだけで応えること
- リアクションだけの返答の LLM 入力を「LLM 入力を見る」で見せること。このメニューは bot のページを対象に記録を引くので（`inspectInputCommand.ts`）、ページの無い返答には開く場所が無い

**将来別 change 候補:**

- 判定で黙ると決まった発言のうち、bot の回答への礼に、決まった絵文字でリアクションする（モデルを呼ばない）

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| モデルが「リアクションだけ」を選ぶ手段 | 専用の client tool `reply_with_reaction`（引数は絵文字だけ）を足す。成功すると、そのターンでモデルの呼び出しを打ち切る | `add_reaction` を呼んでから空の本文で終える案は、モデルの呼び出しが 1 回余分にかかり、空の本文を返すかがモデル次第になる。モデルは tool の結果を受けて何か書き足しがちで、空の本文は今はエラーも表すので、意図した空とモデルの失敗を区別できない。専用の tool なら、終える意図が呼び出しそのものに表れる |
| 本文の有無の判定 | リクエスト全体で見る。打ち切った時点で、前のターンの前置きを含めて本文に空白以外の文字が 1 文字でもあれば、本文の返答として描画し、リアクションも付ける。無いときだけ、リアクションだけの返答として終える | 表示する本文は、前のターンの前置きを積み上げたものである（`messageCreate.ts` の最終描画が使う `updater.text`）。そのターンだけで判定すると、表示済みの前置きを消すかどうかが決まらない。空白を本文に数えないのは、tool の呼び出しの前に改行だけを流すモデルで、中身の無いページが残らないようにするためである |
| 推論 | リアクションだけの返答では、推論を表示しない | 推論は最後にまとめて本文の上に描画するので（`toolLoop.ts` が蓄積し、`messageCreate.ts` の最終描画で表示）、本文の無い返答には置く場所が無い。推論だけのページを出すと、リアクションだけで応えるという目的に反する |
| 同じターンの他の tool | 同じターンで呼ばれた他の tool の結果を待ってから打ち切る | 打ち切りを先にすると、実行中の tool の結果が捨てられ、作業の途中で終わる |
| tool の失敗 | 権限不足などで付けられなかったときは、失敗をモデルに返して呼び出しを続け、本文で返答させる | 失敗したまま本文も無いと、利用者には何も届かない |
| 提供する条件 | `add_reaction` と同じ条件（「機能 → Discord 操作」の設定、tool 対応モデル、テキストチャンネルかスレッド）で、メンションされた発言と自動応答の判定を通った発言の両方に提供する。`ctx.discord` を渡すのはチャンネルの発言への返答（`messageCreate.ts`）だけなので、`isEnabled` は `add_reaction` と同じでよい。モデルごとの許可リストは持たない | ギルドはどのモデルでも設定できるので、モデルごとの許可リストは保守できない |
| 実装に進む条件 | 下の評価で、採用する指示の文面のまま、本文が要る発言（質問、依頼）にリアクションだけで応えた例が 0 件であること。文面を直しても 0 件にならなければ実装せず、この design を `investigating` に戻す | 質問にリアクションだけを返す誤りは、本文で返す誤りより利用者の害が大きく、答えを待っている利用者には何も届かない。自動応答の判定を通った発言だけに絞って提供する案は採らない。判定は bot の回答への礼や相づちを黙る側に置いているので、判定を通る礼は少なく、この機能が役立つ場面の多くはメンションされた礼である |
| モデルへの指示 | tool の説明に、今回の発言が答えも作業も求めておらず、リアクションだけで応えれば足りるとき（礼、了解、相づち）に限って使い、質問や依頼には使わないことを書く。自動応答の判定を通った返答への system 指示にも、答えるべき内容が無ければこの tool で応えてよいことを足す | 判定を通った発言は判定が返答すべきとしたものだが、判定の境目にある発言には相づちも含まれる |
| 「生成中...」の表示 | 最初のメッセージの送信を遅らせる。本文の最初の文字、`reply_with_reaction` 以外の tool の呼び出し、待ち時間 T の経過のうち、最も早いものが来たときに送る。T までにモデルが `reply_with_reaction` を呼べば、何も送らない | 先に送ってから消す案は、「生成中...」が一瞬出て消える。他の tool を呼んだときに送るのは、tool の実行とその後のモデルの呼び出しで返答が長引き、T を待たずに処理中であることを見せたいからである。そのため、他の tool を呼んだ後のリアクションだけの返答では「生成中...」が出てから消える。遅らせる間は停止ボタンが無いが、T は数秒以内に収める（下の T の決め方）ので、止めたい内容がまだ表示されていない |
| T の決め方 | T の起点は、生成を始めた時点（`generateChatResponse` の呼び出し）とする。T は、評価スクリプトで測る、生成の開始からモデルの `reply_with_reaction` の呼び出しを受け取るまでの時間の 90 パーセンタイルとし、3 秒を上限とする。2026-11-08 の測定では 90 パーセンタイルが Haiku と DeepSeek で 2.5 秒以内、Gemini と GLM で 4 秒以上だったので、T は 3 秒とする。`reply_with_reaction` の実行中は時間切れにせず、失敗してモデルを呼び直すときに同じ期限で掛け直す | 上限を置くのは、すべての返答で「生成中...」が出るまでの時間が T だけ延びうるからである。実行中を時間切れにしないのは、権限の確認で REST を数回呼ぶためリアクションを付け終えるまで 1.3 秒から 1.9 秒かかり（E2E の `reaction-only` で測定）、この時間を T に含めると 3 秒の上限に収まらず、すぐ消すページが多くの返答で一瞬見えるからである。実行中は生成が止まっているので、停止ボタンが無くても止めたい内容は無い |
| 遅らせる範囲 | 「機能 → Discord 操作」が有効なギルドの返答だけ | 無効なギルドでは `reply_with_reaction` を提供しないので、遅らせても何も得られず、「生成中...」が出るまでの時間だけが延びる。有効なギルドで tool 非対応のモデルや対象外のチャンネルを除くことはしない。その判定はモデルの情報を引いた後の `chatService.ts` にあり、遅らせる側へ条件を写すと 2 か所で保守することになる。除かない場合の影響は T の分の遅れだけである |
| 入力中の表示（typing） | 使わない | Discord の入力中の表示は、送ってから約 10 秒、またはメッセージが届くまで消せない。リアクションだけで終えた後も、何も届かないまま表示が残る |
| 「生成中...」を送った後にリアクションだけで終えた場合 | 送ったページを、今の不要なページと同じ処理（`createDeleteOwnMessage`: ページの記録を外してから削除し、失敗したら「（このメッセージは不要になりました）」に書き換える）で片付ける | T を超えるモデルでは起きうる。片付けの処理は、返答の途中で不要になったページのために既にある |
| 返答の記録 | 本文が無く終えたら、ページの片付けの後に、保留中の返答の記録をページの無いまま消す（`deletePendingWithoutPages`、判定で黙るときと同じ）。ページの記録が外せずに残ったときは、記録を `failed` で確定する | 記録を消すか `failed` で確定すると、会話の窓では返答の無い普通の発言として扱われる。`completed` を 0 ページで確定する案は、窓が返答を確認できない発言（`unconfirmable`）として扱い、`list_pins` がその発言を読み飛ばすので採らない |
| 同じ発言の二重処理 | リアクションだけで終えた発言の ID を、判定で黙った発言（`wasSilenced`）と同じく 1 時間メモリに持ち、同じ発言のイベントがもう一度届いたら処理しない。持つ場所は `createMessageCreateHandler` の中とする | 今は、保留中の返答の記録があることで同じ発言の二重処理を止めている（`messageCreate.ts` の `createPending` と `findByTrigger`）。記録を消すと、この止め方が効かなくなる。判定で黙るときも記録を消すので、同じ方法で止める。`IReplyGateService` に持たせないのは、メンションされた発言には判定が動かず、判定を設定していない構成でも使うからである |
| 自分のリアクションの見分け方 | Discord の REST がリアクションごとに返す `me`（読み取ったアカウントがその絵文字を付けたか）を読み、`[リアクション 👍 2（Bot も付けた）]` のように書く。discord.js のキャッシュから作る発言（`toRawDiscordMessage`）も、`MessageReaction.me` から同じ値を写す。会話の安全指示に、この表記は Bot 自身が付けたことを表すと足す | 窓は bot 自身のトークンで発言を読むので、`me` は bot 自身のリアクションを表す。返答の記録に絵文字を保存する案は、列の追加と移行が要り、リアクションだけの返答しか記録できない。`me` なら保存は要らず、本文と一緒に `add_reaction` で付けたリアクションにも同じ表記が付く |
| 返答の判定に渡す情報 | 判定の状態には、リアクションも、リアクションだけで応えたことも渡さない | 判定の状態は今もリアクションを渡していない（`replyGateService.ts` の `formatMessage`）。リアクションだけの返答は、答えの要らない発言に使うものなので、判定から見て bot の返答が無いのは実態に合う。bot の返答が直前にあると次の人の発言が bot への続きとして読まれやすくなる傾向も、増やさずに済む |
| 費用の見え方 | リアクションだけで終えたときは、使用量と費用、モデル、絵文字、支払いの元（`payer.source`）を info のログ `Reaction-only reply` に残す。支払いは本文の返答と同じで、`/connect` で接続した本人のキーで払う発言ならそのキーが払う | 本文の返答では費用を LLM 詳細表示の footer で見せているが、リアクションだけの返答には footer を置く場所が無い。ログに残せば、管理 API のログで確認できる。接続したキーで払う発言があるので、誰が払ったかもログに要る |

## Design

### 変更対象ファイル

- 新規: `src/llm/tools/discord/replyWithReaction.ts` — `reply_with_reaction`。今回の発言にリアクションを付け、成功したら打ち切りの指定を返す
- 修正: `src/llm/tools/registry.ts`、`src/llm/tools/toolHandler.ts` — tool の結果に打ち切りの指定を足し、dispatcher の結果まで渡す
- 修正: `src/llm/toolLoop.ts` — client tool の結果が打ち切りの指定を持つとき、同じターンの他の tool の結果を待ってから、次のモデル呼び出しをせずに `final` として終える。本文が空でもエラーにせず、付けた絵文字を結果に持たせる
- 修正: `src/services/chatService.ts` — 自動応答の system 指示への追記、会話の安全指示への `（Bot も付けた）` の説明
- 修正: `src/bot/events/messageCreate.ts` — 最初のメッセージを遅らせて送る。リアクションだけで終えたときのページの片付け、記録の処理、二重処理の記憶、ログ。`toRawDiscordMessage` でリアクションの `me` を写す
- 修正: `src/bot/events/streamingUpdater.ts` — 最初のメッセージを、最初に描画が要るとき、または T の経過時に送る形にする
- 修正: `src/utils/discordMessageNormalizer.ts` — `RawDiscordReaction` に `me` を足し、`formatReactions` が `（Bot も付けた）` を付ける
- 新規: `src/llm/tools/defaultRegistry.ts` — bot が提供する tool の一覧。`src/index.ts` の登録をここへ移し、評価スクリプトと共有する
- 新規: `scripts/reaction-only-eval.ts` — リアクションだけで応える判断と、判断までの時間を測る
- 修正: `scripts/e2e/index.ts`、`scripts/e2e/scenarios.ts` — 返答のページを待たない完了条件と、名前を指定したときだけ動くシナリオ `reaction-only`
- 修正: `AGENTS.md` — `reaction-only` シナリオの条件と、実行が要る変更

`src/services/discordActionService.ts` は変更しない。
`addReaction` は `message_ref` を省くと今回の発言を対象にし、権限の確認と回数の上限もそこで行う（`execute` の `ref === undefined`）。
`reply_with_reaction` はこれを呼ぶだけなので、回数の上限（1 応答 3 回）は `add_reaction` と共有し、`chatService.ts` の再試行の判定（`clientToolInvoked`）も既存のラッパーで数える。

### 実装内容

打ち切りの指定は、`IToolHandlerResult` の新しいフィールドとして絵文字を持たせる。
既存の `terminal` は使わない。
`terminal` は「固定長の結果なのでトークンの予約から出してよい」という意味であり、`add_reaction` も立てていて、打ち切りとは関係が無い。

最終描画の判定は `messageCreate.ts` で行う。
`final` の結果が絵文字を持ち、`updater.text` に空白以外の文字が無いときだけ、リアクションだけの返答として扱う。
本文があれば今の最終描画をそのまま通るので、footer も推論も今と同じに出る。

最初のメッセージの送信は、遅らせている間の状態を 1 か所（streaming updater）が持つ。
送信を始めたら、終了の処理（リアクションだけの返答、本文の返答、停止、シャットダウン、エラー）は、その送信の完了を待ってから行う。
こうすると、送信の途中で生成が終わっても、届いたページは終了の処理が片付けるか描画に使う。
ページの記録への登録（`appendPage`）は、保留中の記録を消すより前に済むので、消した後に届いたページが記録に残らないまま放置されることは無い。
例外はシャットダウンで、終了処理は処理中の返答を最大 8 秒しか待たない（`src/index.ts` の `shutdown`）。
その間に送信が終わらなければ、ページは「生成中...」のまま残り、保留中の記録は次の起動で `failed` になる。
これは本文の返答で今も起きることと同じなので、この change では扱わない。

送信を始める前は、ページが 1 つも無い状態で描画の処理を動かさない。
今の処理は未描画の本文があれば足りないページを送るので（`updateStreamingMessages`）、空白だけの前置きを確定した `commitTurn("tool_calls")` からでも、そのままではページが送られる。
遅らせた送信が失敗したときは warn のログを残して生成を続け、次の描画か最終描画が送り直す。
遅らせない経路は今のままで、最初の送信の失敗はエラーとして扱う。

送信を始める前に中断が起きるのは、シャットダウンのときだけである（停止ボタンは送信の後にしか存在しない）。
この場合は何も送らず、記録を保留中のまま残す。
今の停止表示の処理（`updateStoppedMessages`）はページが無いと「（応答なし）」のページを送るので、ページが 0 のときは呼ばない。
保留中の記録は、シャットダウンの前に初期メッセージを送らずに終える今の経路と同じく、次の起動で `failed` になる。
今のシャットダウン処理は、送信の前に `isClosing` を確認しているので、遅らせる経路ではその確認を送信の直前で行う。
送信を始める前に生成がエラーで終わった場合は、今と同じエラー表示の返信を送る。

返答の記録を `failed` で確定する場合は、他の経路と同じく generation の ID も保存する。
記録を消す場合は保存先が無いので、保存しない。

### E2E の完了条件

今の E2E は、すべてのシナリオで返答のページを待って完了とするので、リアクションだけの返答は時間切れになる。
`reaction-only` シナリオは、起動した bot の出力に `Reaction-only reply` のログ行が出たことを完了の合図とする。
モデルが本文で答えたときに時間切れまで待たないよう、完了したページが届いた場合もそこで終え、ページがあることを失敗として報告する。
そのうえで、REST で発言を読み、bot のリアクションが付いていることと、bot の返答のページが無いことを確認する。
発言の `reactions[].me` はテスターのトークンで読むとテスター自身を表すので、bot のリアクションは絵文字ごとのユーザー一覧（`GET .../reactions/{emoji}`）で確認する。
ログ行を使うので、`--no-spawn` では動かない。
footer が無いので、シナリオの費用は `cost unknown` と出る。
実行後の使用量の差分には含まれる。

### 評価スクリプト

`scripts/reaction-only-eval.ts` は、`ChatService.generateChatResponse` を本物の OpenRouter クライアントと tool の一覧で呼び、次の発言を評価対象のモデルに投げる。
system 指示の組み立てと tool の定義を写さずに本番の処理を通すので、文面を直せばそのまま測定に反映され、本番の要求との差も生じない（要求には `openrouter:datetime` のようなサーバーツールも含まれる）。
Discord を読み書きする部分だけをスタブにする。
評価対象は、各社の現行の汎用モデルから選んだ `anthropic/claude-haiku-5.5`、`google/gemini-3.8-flash`、`z-ai/glm-5.3-flash`、`deepseek/deepseek-v4.1-flash`、`google/gemma-4-26b-a4b-it` とする（2026-11-08 に OpenRouter のモデル一覧で、いずれも提供中で tools に対応していることを確認した）。
スクリプトの既定のモデル一覧もこの 5 つにする。

- リアクションだけで足りる発言: bot の回答への礼、了解、相づち
- 本文が要る発言: 質問、依頼、礼に続けて質問を書いた発言

それぞれを、会話履歴ありのメンションされた発言、会話履歴ありの自動応答の判定を通った発言（自動応答の system 指示を付ける）、会話履歴なしのメンションされた発言の 3 通りで投げる。

updater をスタブにして、次の時点で測定を打ち切る（モデルの呼び出しを止めるので、本文の生成に費用がかからない）。

- `beginToolBlock` に `reply_with_reaction` が来たら、リアクションだけの返答として数え、生成の開始からの時間を記録する。この時点は tool の実行の直前なので、T のモデル側の時間と一致する
- `stageContent` に空白以外の文字が来たら、本文の返答として数える。前置きの後に `reply_with_reaction` を呼ぶ応答は本番でも本文の返答になるので、同じ数え方になる

他の tool はスタブの結果を返して続行する。
本文も `reply_with_reaction` も無く空の応答のエラーで終わった回と、60 秒以内に何も書かなかった回は、別に数える。

2026-11-08 に、採用した文面で評価対象の 5 モデルを 5 回ずつ測り、本文が要る発言にリアクションだけで応えた例は 600 回中 0 件だった。
リアクションだけで足りる発言では、Gemma 以外の 4 モデルはほぼすべての回でリアクションだけで応え（300 回中 294 回）、Gemma は自動応答の発言でしか選ばなかった（メンションの発言では 50 回中 0 回で、本文で答えた）。
空の応答のエラーは 0 件だった。
60 秒以内に何も書かなかった回は GLM にだけ出ており、推論が長いためと考えられる（推論の中身は確認していない）。

## Open Questions / Risks

- T の間は「生成中...」が出ないので、推論の長いモデルでは、返答が始まるまで bot が反応していないように見える時間が最大 T だけ延びる。
- 評価は評価対象の 5 モデルでしか測らないので、それ以外のモデルを設定したギルドでの誤用の率は分からない。
- 評価の回数を増やすと、誤用は 0 にならない。同じ文面で GLM、Gemma、DeepSeek を 20 回ずつ測ると、本文が要る発言 1440 回のうち 1 件で誤用があった（Gemma、自動応答の発言「これってどう思う？」）。実装に進む条件は 5 回ずつの測定で判定しており、この 1 件は条件の外にある。Gemma で自動応答の指示が付くのは、有料の Gemma を設定し、自動応答の判定を有効にしたギルドだけである（無料モデル限定のギルドでは判定が動かず、指示も付かない）。
- `add_reaction` を呼んだ後に本文を書かないモデルは、今と同じく空の応答のエラーになる。評価では該当する回は無かった。
- 「機能 → Discord 操作」が有効なギルドでは、tool 非対応のモデルや対象外のチャンネルでも、本文が届くまで最大 T の間「生成中...」が出ない。
