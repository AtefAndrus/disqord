# リアクションだけで応える返答

## Why

メンションされた発言と、自動応答の判定で返答すると決まった発言には、bot は必ず本文で返答していた。
その中には「ありがとう」「了解」のように、bot に答えも作業も求めていない発言も含まれる。
人どうしの会話なら、こうした発言にはリアクションだけで応えることが多く、本文の返答は会話に割り込んだように見える。

## 依存 / 関連 change

- 連携: [reply-gate-tuning](https://github.com/AtefAndrus/disqord/blob/ebb1c6b95ec976b3c76abf215cbdb167ccb23a2b/docs/changes/reply-gate-tuning/design.md)（v1.16.0 でリリース済み）— 自動応答の判定は、bot の回答への礼や相づちを黙る側に置いている。本 change は、判定を通った発言とメンションされた発言の中で、本文の要らないものを扱う
- 連携: [discord-expressions](../discord-expressions/design.md) — リアクションは `add_reaction` と同じ処理でカスタム絵文字を名前で引くので、そちらの変更がそのまま適用される

## Goals / Non-Goals

**Goals:**

- メンションされた発言と、自動応答の判定を通った発言に、リアクションだけで応えられるようにする
- リアクションだけで応えるときは、通常モデルを呼ばず、「生成中...」のメッセージも表示しない
- 次の返答で、モデルが自分のリアクションを他の人のリアクションと区別して読めるようにする

**Non-Goals:**

- 自動応答の判定で黙ると決まった発言にリアクションを付けること。人どうしの会話に bot のリアクションが並ぶことになり、判定が黙る側に置いた理由と合わない
- 定期実行、コンテキストメニュー（解説、LLM 入力の表示）など、チャンネルの発言への返答以外の経路
- リアクションだけの返答の LLM 入力を「LLM 入力を見る」で見せること。通常モデルを呼んでおらず、見せる生成が無い

**将来別 change 候補:**

- 判定で黙ると決まった発言のうち、bot の回答への礼にリアクションする

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| 誰が決めるか | 判定モデル Jev（`typesafe/jev-1.14`）が、通常モデルを呼ぶ前に決める | 下の測定のとおり、誤用が最も少なく、判断が速く、ギルドのモデル設定に依存しない。最初のページを遅らせて後から消す処理も要らない |
| 通常モデルに tool で決めさせる案 | 採らない | 最初のページを遅らせる状態管理と tool による応答の打ち切りが要るうえ、誤用が多い（`validation` で 6/99 から 13/99）。モデルによって振る舞いも変わり、Gemma はメンションの礼でほとんど選ばない。tool の説明に提案への承諾の区別を足せば誤用は減る可能性があるが（未測定）、状態管理と打ち切りとモデルごとの差は残る |
| Jev と tool を併用する案 | 採らない | 取りこぼしは減るが、tool の案の複雑さが全部残り、誤用も両方の分だけ起きうる |
| 間違いの扱い | 本文の側に倒す | 本文が要る発言にリアクションだけで応えると利用者に答えが届かない（誤用）。足りる発言に本文で答えるのは、この機能が無いときと同じ振る舞いである（取りこぼし） |
| 聞くこと | 1 回のリクエストで `needs_text`（本文が要るか）、`accepts`（Bot の具体的な提案や質問に応じて続きを求めているか）、`emoji`（絵文字）を聞く。`needs_text < 0.3` かつ `accepts < 0.4` のときだけリアクションにする | `needs_text` だけでは、Bot の提案への「了解」「よろしく」「助かる」を礼と読む（87 回中 28 回）。`needs_text` の文面に提案のことを書いても変わらなかった |
| 絵文字の選択肢 | API の上限の 255 個で埋める。組み込みの一覧の前にサーバーのカスタム絵文字を最大 100 個置き、255 個で切る | よく使う絵文字が一覧の先頭にあるので、カスタム絵文字が多くても残る。Unicode の絵文字を機械的に並べると「おやすみ」に ⌚ を選んだので、一覧は顔、手、ハート、身近なものに絞る。カスタム絵文字は名前が意味を表すものなら選ばれる（名前を模した候補で「草」に `kusa`、「すごい」に `sugoi`） |
| Jev に聞かない発言 | 添付、投票、400 文字を超える発言は聞かずに本文にする。長さは、メンションを判定の状態と同じ名前に置き換えた後で数える | 判定の状態は各発言の先頭 400 文字しか持たないので、長い発言の後ろの質問が見えない。メンションを除いて数えると、置き換えで 400 文字を超えた発言の末尾が切れる。添付と投票は本文の内容によらず応答を求めていることが多い |
| Jev を呼ばないギルド | 「機能 → Discord 操作」が無効なギルドと無料モデル限定のギルド | リアクションは Discord 操作の一部である。Jev は有料なので、自動応答の判定と同じく無料モデル限定のギルドでは呼ばない |
| 会話履歴との関係 | 会話の窓を読めた発言にだけ聞く。会話履歴が無効なギルド、窓を取得できなかった発言、返信先を読めなかった返信、窓に Bot の発言が無い発言、判定の状態の上限（直近 20 件、推定 3000 トークン）で Bot の最後の発言が状態から落ちる発言は本文にする | 履歴、返信先、Bot の最後の発言が無いと、提案への「了解」と説明への「了解」が同じ入力になり、閾値では区別できない。本文なら何を続けるかを聞き返せるが、リアクションだけではそこで終わる |
| Bot の長い発言 | Bot の最後の発言（返信先が Bot ならそれ）が 400 文字を超えるときは、末尾 400 文字を `last_bot_message_end` として状態に足す | 判定の状態は発言の先頭しか持たないが、長い回答の提案は末尾に来る。足さないと、長い回答の提案への「よろしく」「嬉しい」がリアクションになった。自動応答の判定の状態は、閾値の調整に使った形のまま変えない |
| 自動応答との関係 | 今の判定が返答すると決めた発言にだけ、別のリクエストで聞く | 判定と同じリクエストに質問を足すと、判定の結果が 102 件中 1 件変わった。判定の閾値は今の形で調整されている |
| 失敗したとき | タイムアウト（1.5 秒）、エラー、拒否、一覧に無い絵文字、リアクションの付与の失敗は、すべて本文にする | 待ち時間は本文の返答の最初のページの遅れになるので短くする。判断時間は 90 パーセンタイルで 0.36 秒である |
| 権限 | `DiscordActionService.addReaction` を通す | 権限の確認と回数の上限を `add_reaction` と共有する。権限が無ければ本文になる |
| 支払い | 発言の支払い元（`payer`）のキーで Jev を呼ぶ | 本文の返答と同じである |
| 費用の見え方 | 判定ごとに info のログ `Reaction gate`（判定の値、絵文字、費用、支払いの元）を残し、リアクションだけで終えたら `Reaction-only reply` を残す | リアクションだけの返答には footer を置く場所が無い |
| 返答の記録 | 判定の後に、保留中の記録を消す（`deletePendingWithoutPages`、判定で黙るときと同じ）。消せないときは `failed` で確定する | 記録を消すか `failed` で確定すると、会話の窓では返答の無い普通の発言として扱われる。`completed` を 0 ページで確定する案は、窓が返答を確認できない発言（`unconfirmable`）として扱い、`list_pins` がその発言を読み飛ばすので採らない |
| 同じ発言の二重処理 | リアクションだけで終えた発言の ID を 1 時間メモリに持ち、`createPending` の前と、`createPending` が false を返した後に確認する。記憶への登録は記録を消す前に行う | 今は保留中の記録があることで二重処理を止めているが（`createPending` と `findByTrigger`）、記録を消すとこの止め方が効かない。先行の処理が記録を消す瞬間に、再送がどの段階にあっても、記憶と記録のどちらかに当たる |
| 自分のリアクションの見分け方 | Discord の REST がリアクションごとに返す `me` を読み、`[リアクション 👍 2（Bot も付けた）]` のように書く。discord.js のキャッシュから作る発言（`toRawDiscordMessage`）も `MessageReaction.me` を写す。会話の安全指示に、この表記の意味を足す | 窓は bot 自身のトークンで発言を読むので、`me` は bot 自身のリアクションを表す。保存が要らず、`add_reaction` で付けたリアクションにも同じ表記が付く |
| 自動応答の判定に渡す情報 | 判定の状態には、リアクションも、リアクションだけで応えたことも渡さない | 判定の状態は今もリアクションを渡していない（`replyGateService.ts` の `formatMessage`）。bot の返答が直前にあると次の人の発言が bot への続きとして読まれやすくなる傾向も、増やさずに済む |

## Design

### 変更対象ファイル

- 新規: `src/services/reactionGateService.ts` — Jev への質問、閾値、`last_bot_message_end`、判定のログ
- 新規: `src/services/reactionEmoji.ts` — 絵文字の一覧。2026-11-09 に全件が Discord に受理されることを確認した
- 修正: `src/llm/openrouter.ts` — Decisions API の `choice` の型と、回答をそのまま返す `decide`
- 修正: `src/bot/events/messageCreate.ts` — 通常モデルを呼ぶ前の判定、リアクションの付与、記録の処理、二重処理の記憶
- 修正: `src/services/chatService.ts` — 会話の安全指示への `（Bot も付けた）` の説明
- 修正: `src/utils/discordMessageNormalizer.ts` — `RawDiscordReaction` の `me` と `formatReactions` の表記
- 修正: `src/index.ts` — サービスの組み立て
- 新規: `scripts/reaction-gate-cases.ts`、`scripts/reaction-gate-eval.ts` — 手書きの発言と評価
- 修正: `scripts/e2e/index.ts`、`scripts/e2e/runner.ts`、`scripts/e2e/scenarios.ts` — 返答のページを待たない完了条件と、名前を指定したときだけ動くシナリオ `reaction-only`
- 修正: `AGENTS.md` — `reaction-only` シナリオの条件と評価のコマンド

### 流れ

1. 発言が届く。自動応答なら、今の判定で返答するかを決める（黙るならここで終わり）。
2. 会話の窓を読み、Jev に聞く対象なら判定する（約 0.3 秒）。
3. リアクションと決まれば `addReaction` で付け（約 1.5 秒）、記録を消し、ログを残して終わる。ページは送らず、通常モデルも呼ばない。
4. 本文と決まったとき、対象外のとき、どこかで失敗したときは、今までどおり「生成中...」を送って通常モデルを呼ぶ。

シャットダウンが始まっていたら、絵文字が決まっていてもリアクションを付けない。

### E2E の完了条件

今の E2E は、すべてのシナリオで返答のページを待って完了とするので、リアクションだけの返答は時間切れになる。
判定は会話に Bot の発言があるときだけ聞くので、`reaction-only` は `reaction-only-answer` の返答の直後に流す。
`reaction-only` シナリオは、起動した bot の出力に `Reaction-only reply` のログ行が出たことを完了の合図とする。
判定が本文を選んだときに時間切れまで待たないよう、完了したページが届いた場合もそこで終え、ページがあることを失敗として報告する。
そのうえで、REST で発言を読み、bot のリアクションが付いていることと、bot の返答のページが無いことを確認する。
発言の `reactions[].me` はテスターのトークンで読むとテスター自身を表すので、bot のリアクションは絵文字ごとのユーザー一覧（`GET .../reactions/{emoji}`）で確認する。
ログ行を使うので、`--no-spawn` では動かない。

### 測定

`bun scripts/reaction-gate-eval.ts --runs 3` は、`scripts/reaction-gate-cases.ts` の発言を、bot が組み立てるのと同じ状態と質問で Jev に投げる。
発言は、本文が要るものとリアクションで足りるものを手で分け、どちらでもよいものは数えない。
`validation` は、最初の実行の時点で文面を固定していたセットである（閾値は `needs_text` 0.3、`accepts` 0.45）。
その後 `accepts` を開発用の発言の結果で 0.4 に下げた。下げても本文に回る方向にしか動かないので、`validation` の誤用は増えない。

通常モデルとの比較は、会話履歴つきのメンションの発言を各 3 回投げて、2026-11-09 に行った。
通常モデルの測定は、`reply_with_reaction` を渡した本番の `ChatService` を通し、60 秒で打ち切った。
時間切れは全 168 試行のうち `z-ai/glm-5.3-flash` で 22、`google/gemini-3.8-flash` で 1 あり、最終的に何を選んだかは分からない。表の通常モデルの値は、60 秒以内に観測した結果である。

| 方式 | 誤用（`validation`） | 取りこぼし（`validation`） |
| --- | --- | --- |
| Jev | 0/99 | 4/57 |
| `google/gemini-3.8-flash` | 6/99 | 12/57 |
| `deepseek/deepseek-v4.1-flash` | 8/99 | 14/57 |
| `anthropic/claude-haiku-5.5` | 10/99 | 14/57 |
| `z-ai/glm-5.3-flash` | 13/99 | 6/57 |

Jev の全セット（採点対象 252 発言）では、誤用 0/465、取りこぼし 37/291 である。
同じ実行で `accepts` の閾値を 0.5 にすると誤用が 7/465、0.55 で 11/465 に増える。別の実行では 0.45 で 1/465 だった。
既存の自動応答の判定ケース（102 件）では、返答すべきで判定を通った発言がリアクションだけになるものは無かった（`last_bot_message_end` を足す前の、`accepts` 0.45 での測定）。

判断時間は Jev が全試行の 90 パーセンタイルで 0.36 秒、1 回 $0.0001 である。
通常モデルはリアクションを選んだ試行だけの 90 パーセンタイルで、`validation` では 3.0 秒から 12.7 秒だった。
Jev は 6 並列、通常モデルは各モデル 12 並列で 4 モデルを同時に測ったので、差のうち負荷の条件による分は分からない。

## Open Questions / Risks

- 測定は手書きの発言で、会話履歴つきのメンションだけである。本番の発言の分布では測っていない。自動応答の発言は、誤用の測定が足りない。ログ `Reaction gate` に判定の値が残るので、リリース後に実際の発言で確認できる。
- Bot の長い発言の提案が、先頭 400 文字と末尾 400 文字のどちらにも入らない場合（提案の後に長い補足やコードが続く場合）は、Jev に見えない。提案は末尾に来るのが普通なので本文に倒す条件にはしていないが、この形の誤用の率は測っていない。`last_bot_message_end` を長くすれば狭められるが、閾値の再評価が要る。
- 承諾先が Bot の最後の発言でない場合（Bot が別の人に答えた後で、前の提案に返信なしで応じる場合）は、古い提案が状態に残っていても `accepts` が最後の発言を見るので、誤用になりうる。この形の率は測っていない。
- 取りこぼしが全体で約 13% ある。Bot の説明への「助かりました」「なるほどねー」が `accepts` で本文に回る。
- 文脈に合わせた表現は通常モデルより狭い。名前が意味を表さないカスタム絵文字は選ばれにくい見込みである（未検証）。
- `/api/alpha/decisions` は alpha であり、形が変わる可能性がある。回答を読めなければ本文になる。
- 無料モデル限定のギルドと、会話履歴が無効なギルドでは機能が使えない。
- メンションの発言のうち対象のものは、最初のページが判定の分（約 0.3 秒）遅れ、Jev の費用（1 回 $0.0001）が加わる。
