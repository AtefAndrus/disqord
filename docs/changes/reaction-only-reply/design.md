# リアクションだけで応える返答

## Why

メンションされた発言と、自動応答の判定で返答すると決まった発言には、bot は今は必ず本文で返答する。
その中には「ありがとう」「了解」のように、bot に答えも作業も求めていない発言も含まれる。
人どうしの会話なら、こうした発言にはリアクションだけで応えることが多く、本文の返答は会話に割り込んだように見える。

今の仕組みでは、モデルがリアクションだけで済ませようとしても成立しない。
モデルが `add_reaction` を呼ぶと必ず次のモデル呼び出しが続き（`src/llm/toolLoop.ts` の tool 呼び出し後の `continue`）、その呼び出しが本文を返さないと、空の応答としてエラーになる（同ファイルの、`finish_reason` が `stop` で本文が空のときの処理）。
利用者には、リアクションに加えて、エラー ID 付きのエラー表示の返信が届く。

## 依存 / 関連 change

- 連携: [reply-gate-tuning](https://github.com/AtefAndrus/disqord/blob/ebb1c6b95ec976b3c76abf215cbdb167ccb23a2b/docs/changes/reply-gate-tuning/design.md)（v1.16.0 でリリース済み）— 自動応答の判定は、bot の回答への礼や相づちを黙る側に置いている。本 change は、判定を通った発言とメンションされた発言の中で、本文の要らないものを扱う

## Goals / Non-Goals

**Goals:**

- メンションされた発言と、自動応答の判定を通った発言に、モデルの判断でリアクションだけで応えられるようにする
- リアクションだけの返答が、他の tool を呼ばずに待ち時間 T のうちに終わったときは、「生成中...」のメッセージを表示しない
- 次の返答で、モデルが自分のリアクションを他の人のリアクションと区別して読めるようにする

**Non-Goals:**

- 自動応答の判定で黙ると決まった発言にリアクションを付けること。判定はリアクションの絵文字を選べず、選ぶにはモデルの呼び出しが要るので、黙る判定で節約している費用が無くなる
- 定期実行、コンテキストメニュー（解説、LLM 入力の表示）など、チャンネルの発言への返答以外の経路
- 現在の発言以外の発言にリアクションだけで応えること

**将来別 change 候補:**

- 判定で黙ると決まった発言のうち、bot の回答への礼に、決まった絵文字でリアクションする（モデルを呼ばない）

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| モデルが「リアクションだけ」を選ぶ手段 | 専用の client tool `reply_with_reaction`（引数は絵文字だけ）を足す。成功すると、そのターンでモデルの呼び出しを打ち切る | `add_reaction` を呼んでから空の本文で終える案は、モデルの呼び出しが 1 回余分にかかり、空の本文を返すかがモデル次第になる。モデルは tool の結果を受けて何か書き足しがちで、空の本文は今はエラーの印でもあるので、意図した空とモデルの失敗を区別できない。専用の tool なら、終える意図が呼び出しそのものに表れる |
| 本文の有無の判定 | リクエスト全体で見る。打ち切った時点で、前のターンの前置きを含めて本文が 1 文字でもあれば、本文の返答として描画し、リアクションも付ける。本文が無いときだけ、リアクションだけの返答として終える | 表示する本文は、前のターンの前置きを積み上げたものである（`messageCreate.ts` の最終描画が使う `updater.text`）。そのターンだけで判定すると、表示済みの前置きを消すかどうかが決まらない |
| 推論 | リアクションだけの返答では、推論を表示しない | 推論は最後にまとめて本文の上に描画するので（`toolLoop.ts` が蓄積し、`messageCreate.ts` の最終描画で表示）、本文の無い返答には置く場所が無い。推論だけのページを出すと、リアクションだけで応えるという目的に反する |
| 同じターンの他の tool | 同じターンで呼ばれた他の tool の結果を待ってから打ち切る | 打ち切りを先にすると、実行中の tool の結果が捨てられ、作業の途中で終わる |
| tool の失敗 | 権限不足などで付けられなかったときは、失敗をモデルに返して呼び出しを続け、本文で返答させる | 失敗したまま本文も無いと、利用者には何も届かない |
| 提供する条件 | `add_reaction` と同じ条件（「機能 → Discord 操作」の設定、tool 対応モデル、テキストチャンネルかスレッド）で、チャンネルの発言への返答のときだけ、メンションされた発言と自動応答の判定を通った発言の両方に提供する。モデルごとの許可リストは持たない | ギルドはどのモデルでも設定できるので、モデルごとの許可リストは保守できない |
| 実装に進む条件 | 下の評価で、採用する指示の文面のまま、本文が要る発言（質問、依頼）にリアクションだけで応えた例が 0 件であること。文面を直しても 0 件にならなければ実装せず、この design を `investigating` に戻す | 質問にリアクションだけを返す誤りは、本文で返す誤りより利用者の害が大きく、答えを待っている利用者には何も届かない。自動応答の判定を通った発言だけに絞って提供する案は採らない。判定は bot の回答への礼や相づちを黙る側に置いているので、判定を通る礼は少なく、この機能が役立つ場面の多くはメンションされた礼である |
| モデルへの指示 | tool の説明に、今回の発言が答えも作業も求めておらず、リアクションだけで応えれば足りるとき（礼、了解、相づち）に限って使い、質問や依頼には使わないことを書く。自動応答の判定を通った返答への system 指示にも、答えるべき内容が無ければこの tool で応えてよいことを足す | 判定を通った発言は判定が返答すべきとしたものだが、判定の境目にある発言には相づちも含まれる |
| 「生成中...」の表示 | 最初のメッセージの送信を遅らせる。本文の最初の文字、`reply_with_reaction` 以外の tool の呼び出し、待ち時間 T の経過のうち、最も早いものが来たときに送る。T までにリアクションだけの返答として終われば、何も送らない | 先に送ってから消す案は、「生成中...」が一瞬出て消える。他の tool を呼んだときに送るのは、tool の実行とその後のモデルの呼び出しで返答が長引き、T を待たずに処理中であることを見せたいからである。そのため、他の tool を呼んだ後のリアクションだけの返答では「生成中...」が出てから消える。遅らせる間は停止ボタンが無いが、T は数秒以内に収める（下の T の決め方）ので、止めたい内容がまだ表示されていない |
| T の決め方 | T の起点は、生成を始めた時点（`generateChatResponse` の呼び出し）とする。T は次の二つの 90 パーセンタイルの和とし、3 秒を上限とする。一つは、評価スクリプトで測る、生成の開始からモデルの `reply_with_reaction` の呼び出しを受け取るまでの時間である。もう一つは、E2E の `reaction-only` シナリオで、bot のログの `Tool call` 行が記録する `reply_with_reaction` の実行時間（tool の実行開始からリアクションを付け終えるまで）である | 何も送らずに終えるには、モデルの判断に加えて、権限の確認とリアクションの送信まで T のうちに終わる必要がある。二つの時間は重ならないので、和で足りる。上限を置くのは、すべての返答で「生成中...」が出るまでの時間が T だけ延びうるからである |
| 遅らせる範囲 | 「機能 → Discord 操作」が有効なギルドの返答だけ | 無効なギルドでは `reply_with_reaction` を提供しないので、遅らせても何も得られず、「生成中...」が出るまでの時間だけが延びる |
| 入力中の表示（typing） | 使わない | Discord の入力中の表示は、送ってから約 10 秒、またはメッセージが届くまで消せない。リアクションだけで終えた後も、何も届かないまま表示が残る |
| 「生成中...」を送った後にリアクションだけで終えた場合 | 送ったページを、今の不要なページと同じ処理（`createDeleteOwnMessage`: ページの記録を外してから削除し、失敗したら「（このメッセージは不要になりました）」に書き換える）で片付ける | T を超えるモデルでは起きうる。片付けの処理は、返答の途中で不要になったページのために既にある |
| 返答の記録 | 本文が無く終えたら、ページの片付けの後に、保留中の返答の記録をページの無いまま消す（`deletePendingWithoutPages`、判定で黙るときと同じ）。ページの記録が外せずに残ったときは、記録を `failed` で確定する | 記録を消すか `failed` で確定すると、会話の窓では返答の無い普通の発言として扱われる。`completed` を 0 ページで確定する案は、窓が返答を確かめられない発言（`unconfirmable`）として扱い、`list_pins` がその発言を読み飛ばすので採らない |
| 同じ発言の二重処理 | リアクションだけで終えた発言の ID を、判定で黙った発言（`wasSilenced`）と同じく 1 時間メモリに持ち、同じ発言のイベントがもう一度届いたら処理しない | 今は、保留中の返答の記録があることで同じ発言の二重処理を止めている（`messageCreate.ts` の `createPending` と `findByTrigger`）。記録を消すと、この止め方が効かなくなる。判定で黙るときも記録を消すので、同じ方法で止める |
| 自分のリアクションの見分け方 | Discord の REST がリアクションごとに返す `me`（読み取ったアカウントがその絵文字を付けたか）を読み、`[リアクション 👍 2（Bot も付けた）]` のように書く。discord.js のキャッシュから作る発言（`toRawDiscordMessage`）も、`MessageReaction.me` から同じ値を写す。会話の安全指示に、この印は Bot 自身が付けたことを表すと足す | 窓は bot 自身のトークンで発言を読むので、`me` は bot 自身のリアクションを表す。返答の記録に絵文字を保存する案は、列の追加と移行が要り、リアクションだけの返答しか記録できない。`me` なら保存は要らず、本文と一緒に `add_reaction` で付けたリアクションにも同じ印が付く |
| 返答の判定に渡す情報 | 判定の状態には、リアクションも、リアクションだけで応えたことも渡さない | 判定の状態は今もリアクションを渡していない（`replyGateService.ts` の `formatMessage`）。リアクションだけの返答は、答えの要らない発言に使うものなので、判定から見て bot の返答が無いのは実態に合う。bot の返答が直前にあると次の人の発言が bot への続きとして読まれやすくなる傾向も、増やさずに済む |
| 費用の見え方 | リアクションだけで終えたときは、使用量と費用、モデル、絵文字を info のログ `Reaction-only reply` に残す | 本文の返答では費用を LLM 詳細表示の footer で見せているが、リアクションだけの返答には footer を置く場所が無い。ログに残せば、管理 API のログで確かめられる |

## Design

### 変更対象ファイル

- 新規: `src/llm/tools/discord/replyWithReaction.ts` — `reply_with_reaction`。今回の発言にリアクションを付け、成功したら打ち切りの印を返す
- 修正: `src/llm/toolLoop.ts` — client tool の結果が打ち切りの印を持つとき、同じターンの他の tool の結果を待ってから、次のモデル呼び出しをせずに `final` として終える。本文が空でもエラーにせず、リアクションだけで終えたことを結果に持たせる
- 修正: `src/services/chatService.ts` — tool の登録と提供の条件、自動応答の system 指示への追記、会話の安全指示への `（Bot も付けた）` の説明、リアクションだけの印の受け渡し
- 修正: `src/services/discordActionService.ts` — 今回の発言へのリアクションを、`addReaction` と同じ権限の確認と回数の上限で付ける
- 修正: `src/bot/events/messageCreate.ts` — 最初のメッセージを遅らせて送る。リアクションだけで終えたときのページの片付け、記録の処理、二重処理の記憶、ログ。`toRawDiscordMessage` でリアクションの `me` を写す
- 修正: `src/bot/events/streamingUpdater.ts` — 最初のメッセージを、最初に描画が要るとき、または T の経過時に送る形にする
- 修正: `src/utils/discordMessageNormalizer.ts` — `RawDiscordReaction` に `me` を足し、`formatReactions` が `（Bot も付けた）` を付ける
- 修正: `src/index.ts` — tool の登録
- 新規: `scripts/reaction-only-eval.ts` — リアクションだけで応える判断と、判断までの時間を測る
- 修正: `scripts/e2e/index.ts`、`scripts/e2e/scenarios.ts` — 返答のページを待たない完了条件と、名前を指定したときだけ動くシナリオ `reaction-only`

### 実装内容

最初のメッセージの送信は、遅らせている間の状態を 1 か所（streaming updater）が持つ。
送信を始めたら、終了の処理（リアクションだけの返答、本文の返答、停止、シャットダウン、エラー）は、その送信の完了を待ってから行う。
こうすると、送信の途中で生成が終わっても、届いたページは終了の処理が片付けるか描画に使う。
ページの記録への登録（`appendPage`）は、保留中の記録を消すより前に済むので、消した後に届いたページが記録に残らないまま放置されることは無い。
例外はシャットダウンで、終了処理は処理中の返答を最大 8 秒しか待たない（`src/index.ts` の `shutdown`）。
その間に送信が終わらなければ、ページは「生成中...」のまま残り、保留中の記録は次の起動で `failed` になる。
これは本文の返答で今も起きることと同じなので、この change では扱わない。

送信を始める前に、停止ボタンやシャットダウンによる中断が起きた場合は、何も送らずに中断として扱う。
今のシャットダウン処理は、送信の前に `isClosing` を確かめているので、その確認を送信の直前に移す。
送信を始める前に生成がエラーで終わった場合は、今と同じエラー表示の返信を送る。

### E2E の完了条件

今の E2E は、すべてのシナリオで返答のページを待って完了とするので、リアクションだけの返答は時間切れになる。
`reaction-only` シナリオは、起動した bot の出力に `Reaction-only reply` のログ行が出たことを完了の印とする。
そのうえで、REST で発言を読み、bot のリアクションが付いていることと、bot の返答のページが無いことを確かめる。
ログ行を使うので、`--no-spawn` では動かない。

### 評価スクリプト

`scripts/reaction-only-eval.ts` は、`src/services/chatService.ts` と同じ system 指示と tool の定義で、次の発言を評価対象のモデルに投げる。
評価対象は、各社の現行の汎用モデルから選んだ `anthropic/claude-haiku-5.5`、`google/gemini-3.8-flash`、`z-ai/glm-5.3-flash`、`deepseek/deepseek-v4.1-flash`、`google/gemma-4-26b-a4b-it` とする（2026-10-19 に OpenRouter のモデル一覧で提供を確かめた）。
スクリプトの既定のモデル一覧もこの 5 つにする。

- リアクションだけで足りる発言: bot の回答への礼、了解、相づち
- 本文が要る発言: 質問、依頼、礼に続けて質問を書いた発言

それぞれを、メンションされた発言と、自動応答の判定を通った発言（自動応答の system 指示を付ける）の両方で投げる。
数えるのは、`reply_with_reaction` を選んだ率と、生成の開始からその tool の呼び出しを受け取るまでの時間である。

## Open Questions / Risks

- T の間は「生成中...」が出ないので、推論の長いモデルでは、返答が始まるまで bot が反応していないように見える時間が最大 T だけ延びる。
- 評価は評価対象の 5 モデルでしか測らないので、それ以外のモデルを設定したギルドでの誤用の率は分からない。
