# 数式を画像で表示する

## Why

Discord は TeX の数式を描画しない。
数学の話題では、モデルが `\[ … \]` の別行立ての数式と `\( … \)` の文中の数式を多用し、返答は記号の並んだ読みにくいテキストになる。
別行立ての数式を画像にして本文の該当位置に差し込み、文中の数式は読めるコードの表記にする。

## 依存 / 関連 change

- 連携: [画像生成](../image-generation/design.md) — 同 change の planner（`ResponseLayoutPlanner`）が、返答のページに添付と `MediaGallery` を割り付ける契約と、編集で残す添付を明示する契約を持つ。本 change はその planner に「本文の位置に紐づく画像」を足す拡張として実装する。本 change を先に実装するときは、planner を同 change の仕様どおりに作ったうえで拡張する

## Goals / Non-Goals

**Goals:**

- 返答の本文の別行立ての数式（`$$ … $$` と `\[ … \]`）を PNG にし、最終描画のときに本文の該当位置へ `MediaGallery` で差し込む
- 文中の数式（`$ … $` と `\( … \)`）は、区切りの記号を外してインラインコードにする
- 画像の説明（alt）に元の TeX を入れ、会話の窓が bot の過去の返答を読み戻すときに数式を元の位置へ戻す
- 画像にできない数式は、TeX のコードブロックで表示する

**Non-Goals:**

- 文中の数式の画像化。Discord は文の途中に画像を置けない
- 生成中（ストリーミング中）の数式の描画。画像は最終描画のときに作る
- 数式を Unicode の記号（x²、√ など）へ変換すること。変換できる範囲が狭く、複雑な式では誤った表示になりうる

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| 数式の検出 | 本文を先頭から走査する小さな関数で、コードブロック（フェンス）、インラインコード（バッククォートの連なり）、バックスラッシュのエスケープ、数式の区切り（`$$`、`\[`、`\]`、`$`、`\(`、`\)`）を見分け、本文を「文章」と「別行立ての数式（TeX）」の並びに一度だけ分ける。文中の数式は文章の中に残し、範囲だけを印にする。コードの中、自動リンク（`<https://…>`）の中、リンク先（`[…](…)` の丸括弧の中）、リンクの外の裸の URL（`http://` か `https://` から空白の手前まで。リンク先の中はリンク先の規則で扱い、閉じの丸括弧で終わる）、閉じの区切りが無いもの、中身が空白だけのもの（`$$$$`、`\[ \]`）、区切りの `\` の前にバックスラッシュが奇数個続くもの（`\\[` は、エスケープされたバックスラッシュと `[` であり区切りではない）は数式にしない。`$` の文中の数式は pandoc と同じ規則にする。開きの `$` の直後は空白でなく、閉じの `$` の直前は空白でなく、閉じの `$` の直後は数字でない | 本文を数式の前後で区切るには、元の文字列のどこからどこまでが数式かが要る。ox-content（`@ox-content/napi`）の `parse` は数式とコードを正しく見分けたが、構文木に位置が無い。位置を含む `parseMdastRaw` は独自のバイナリ形式で、読み解く実装が公開パッケージから export されていない（`@ox-content/unplugin` の exports に無い）ので、内部の形式に依存するコードを写して持つことになる。見分ける対象は 4 種類だけなので、自前の走査をテストで固める方が保守しやすい。リンク先を外すのは、Web 検索の結果のリンクが `[見出し](<URL>)` の形で本文に足され（`webSearch.ts`）、URL の中の `$…$` を数式にするとリンク先が変わるためである。Discord は裸の URL もリンクにするので、同じ理由で外す。中身が空白だけの数式を外すのは、描いても何も見えず、`MediaGallery` の項目の説明は 1 字以上でなければならない（discord.js の検証）ためである。`$` の規則は、`$5 と $10` のような金額を数式にせず、`$2+2$` のような数式は数式にするためである。位置を持ち回らずに並びへ分けるのは、後の処理（文中の数式の置き換え、分割器の区切り線の置き換えと改行の正規化）が文字列を変えても、数式の区切りがずれないようにするためである |
| スポイラーの中の数式 | 走査はスポイラー（`\|\|…\|\|`）の範囲も見分け、その中の別行立ての数式は画像にもコードブロックにもせず、元の文章のまま残す。文中の数式はインラインコードに替える | 画像はスポイラーの記号と別の component になり、中身が隠れずに見える。コードブロックはスポイラーで隠れない。インラインコードはスポイラーの中でも隠れる |
| 描画 | MathJax 4 の直接の API（npm の `@mathjax/src`）で TeX を SVG にし、resvg（`@resvg/resvg-js`）で PNG にする。SVG の出力（`SVG`）は 1 つを共有し、TeX の入力（`TeX`）と文書（`mathjax.document`）は数式ごとに新しく作る。TeX の拡張は `base`、`ams`、`newcommand`、`boldsymbol`、`cancel`、`mathtools` を明示して読み込み、`noundefined`、`require`、`autoload`、色の拡張（`color`、`bbox`）は読み込まない。変換は `mathjax.handleRetriesFor` で包み、フォントの追加のデータの読み込みを待つ（`@mathjax/src/js/util/asyncLoad/esm.js` を読み込んでおく）。SVG の `data-latex` 属性は PNG にする前に取り除き、SVG の出力の CSS（`adaptor.cssText(svg.styleSheet(doc))`）を SVG の `<style>` に埋め込む。フォントのファイルは用意しない | TeX の入力は、`\def`、`\newcommand`、`\DeclareMathOperator` の定義と `\label` を後の式にも持ち越し、MathJax の `texReset()` はマクロを消さない。1 つの TeX の入力を共有すると、ある返答の定義やラベルが別の返答の式に効くが、数式ごとに作ればどの定義もその式の中にとどまり、定義の命令を 1 つずつ止める必要がない。2026-09-28 の試行で、TeX の入力を数式ごとに作り SVG の出力を共有すると、前の式の定義は未定義になり、前の式のラベルへの `\ref` は `???` になり、1 式の変換は約 9ms だった（SVG の出力も数式ごとに作ると約 48ms）。npm の `mathjax` のコンポーネントの API（`MathJax.init` と `tex2svgPromise`）は 1 つの TeX の入力を共有するので使わない。拡張を明示するのは、既定の拡張が次の問題を持つためである。`noundefined` は未定義の命令を `merror` にせず命令名の文字として描き、`require` と `autoload` は式の中から拡張を読み込ませる。色の拡張を読み込まないのは、白地の画像で見えない `\color{white}` のような式を作らせないためで、色を指定した式は `merror` になりコードブロックになる（同日の試行で、`\color`、`\textcolor`、`\bbox` は `merror` になり、`\boldsymbol`、`\cancel`、`\coloneqq`、`\operatorname` は描けた）。フォントの追加のデータが要る式（`\mathbb`、`\mathfrak`、`\mathscr`）は、同期の変換では retry の例外（an asynchronous action is required）を投げ、`handleRetriesFor` で包むと描けた。配列の区切り線（`\hline`、`\hdashline`、列の `\|`）は CSS のクラス（`mjx-solid`、`mjx-dashed`）で線を描くので、CSS の無い SVG では線が消え、CSS を埋め込むと resvg で描けた。MathJax 4 の SVG 出力は、内蔵の数式フォントにある字形をパスで描く。2026-09-27 の試行で、分数、`\pmod`、`\tag`、`\boxed`、`cases` を 1 式あたり約 20ms で描けた。内蔵のフォントに無い文字は `<text>` 要素になり、フォントが無いと正しく描けないが、その数式はコードブロックにする（下の「画像にしない数式」）。MathJax 4 は `data-latex` に元の TeX を `<` をエスケープせずに入れ、resvg が SVG として読めずに失敗した（`cases` の `x<0`）。属性を取り除くと描けた |
| 描画の失敗の検出 | MathJax の出力に `merror` の節（`data-mml-node="merror"`）があれば失敗とする。例外と resvg の失敗も失敗とする。未定義の命令は、`noundefined` を読み込まないので `merror` になる（上の「描画」） | MathJax は不正な TeX でも例外を投げず、エラーの表示を数式の出力に埋め込む。2026-09-28 の試行で、`\foo{x}+1` は `noundefined` を読み込むと `merror` にならず、読み込まないと `merror` になった |
| 色と背景 | 白地に黒の文字で、周りに余白を付ける。式の中の色の指定は受け付けない（上の「描画」） | 利用者のテーマ（ライトかダーク）を bot は知らない。透明の背景に明るい文字にすると、ライトテーマで読めない |
| 画像の大きさ | 2 倍の解像度で描く（resvg の `fitTo` を `zoom` の 2 にする）。余白を含めた SVG を resvg に読ませ、描画の前に `width` と `height` に倍率の 2 を掛けて出来上がりの幅と高さを求め、幅が 1600px を超える式と高さが 800px を超える式は描かない。描いた PNG が 1 MiB を超える式も画像にしない | 横に長い式を縮めると読めなくなる。PNG の容量は描いた後にしか分からず、短い TeX でも大きな高さを指定できるので、描画の前に画素数を抑えて resvg のメモリの使用を制限する。resvg の `width` と `height` は拡大の前の SVG の寸法で、拡大の後の寸法は `render()` の結果にしか無い（2026-09-28 の試行で、100×40 の SVG を 2 倍にしたとき、`width` と `height` は 100 と 40、`render()` の結果は 200 と 80 だった） |
| ページの分割 | 分割器は「文章」と「別行立ての数式」の並びを受け取り、文章は今の規則で分け、数式は 1 つの塊として途中で切らない。文中の数式から作ったインラインコードも、途中で切らない塊として渡す。数式は、画像にできずコードブロックにしたときの文字数とバイト数でページの予算に数える。コードブロックは、前後の文章と改行で分け（前の文章が改行で終わっていなければ改行を足し、後ろの文章も改行から始める）、フェンスはバッククォート 3 個に `tex` を付けたものにする。TeX にバッククォートが 3 個以上連なる数式は、コードブロックにせず「数式を表示できませんでした」と書く。足した改行とフェンスも予算に数える。1 つの数式のコードブロックがページの予算を超えるときは画像にせず、本 change の側で TeX を行の境目でページの予算に収まる塊に分け、1 行がそれでも収まらないときはその行を文字の位置で分け、塊ごとにフェンスで囲む。文中の数式のインラインコードがそれだけでページの予算を超えるときは、インラインコードにせず、別行立ての数式と同じコードブロックにする | 今の分割器は文字数とバイト数で本文を切り、コードブロックだけを守るが、フェンスを常にバッククォート 3 個として扱い、インラインコードの開閉を追わない。数式の途中で切ると、どちらのページでも数式として検出できず、生の TeX が残る。描画の失敗や上限の超過は分割の後に分かるので、コードブロックにしてもページの予算を超えないよう、その大きさで先に数える。本 change が作るコードブロックとインラインコードは、分割器の汎用の規則に任せず、塊として扱うか自ら分ける。フェンスをバッククォート 3 個に限るのは、Discord がチルダのフェンスや 4 個以上のバッククォートのフェンスをコードブロックとして表示するかを確かめておらず、今の分割器もバッククォート 3 個のフェンスだけを扱うためである。バッククォートが 3 個以上連なる TeX は数式としてまれで、画像にできなかった場合だけの表示である |
| 配置 | ページの本文を数式の位置で区切り、`TextDisplay` と、数式 1 つにつき 1 つの `MediaGallery` を交互に並べる。空の区切り（数式だけの返答、ページの先頭や末尾の数式）には `TextDisplay` を置かない。区切り線（`---`）だけの区切りは、今の区切り線の扱いと同じく `Separator` にする | `MediaGallery` に複数の画像を入れると横に並ぶ格子になり、式の順が読みにくい。今の組み立ては空の本文を「（応答なし）」に置き換えるので、数式の前後に偽の本文が出ないようにする |
| 上限 | ページごとに、component 40 個と添付 10 件を、`reasoning.md` と画像生成の生成物と合わせて数える。`reasoning.md` と生成物が先に使い、残りに収まる数だけ数式を先頭から画像にし、収まらない数式はコードブロックで表示する。添付の容量は、1 式 1 MiB の上限（上の「画像の大きさ」）で Discord の 1 ファイルの上限（既定 20 MiB）に十分収まる | Discord の 1 メッセージの上限である（[画像生成](../image-generation/design.md) の planner が確かめたもの）。数式の多い証明は 10 式を超えうる |
| 編集での添付と再試行 | 画像生成の planner の送信と編集の契約に従い、数式の画像も planner の生成物として扱う。Discord へ送る編集の `attachments` は、残す既存の添付と今回の新しいファイルの両方を列挙した形になるが、discord.js の `message.edit()` は `files` から新しいファイルの項目を自ら足すので、呼び出し側は `attachments` に残す既存の添付だけを渡し、編集を試みるたびにその配列を新しく作る。最初の編集が失敗したときは同 change の規則（メッセージを取得し直してファイル名で反映済みの添付を確かめ、未反映のものを 1 度だけ再試行する）に従う。再試行でも送れなかった数式の画像は、警告にして除外するのではなく、その数式をコードブロックに替えてページを作り直す | Discord の API v10 の編集では、`attachments` に編集の後も残す添付と新しいファイルを列挙する必要がある。discord.js は新しいファイルの項目を足すので、呼び出し側も新しいファイルを列挙すると ID が重複する。discord.js は項目を渡された配列そのものに足す（`MessagePayload.resolveBody()` の `push`）ので、再試行で同じ配列を渡しても重複する。同じページに `reasoning.md`、生成物、数式の画像が同居しうるので、編集と再試行の規則は planner の 1 か所に置く。数式を除外すると本文の途中から式が消えるが、コードブロックはページの予算に先に数えてあるので、替えてもページに収まる |
| 画像の説明と読み戻し | 数式の画像のファイル名を `math_<requestId>_<連番>.png` にし、`MediaGallery` の項目の説明に元の TeX を入れる。会話の窓は bot の返答を読み戻すとき、`MediaGallery` の項目の `media.url` のパスの最後の区切り（URL のデコードをしたもの）をファイル名とし、ファイル名が `math_` で始まる画像だけを数式とみなす。`media.url` が無いか、そのパスが Discord の添付の形（`/attachments/<channel>/<id>/<ファイル名>`）でない項目は数式とみなさない。編集が失敗した後に反映済みの画像を確かめるときも、同じ方法でファイル名を得る。そのうえで `TextDisplay`、`Separator`、数式の画像を並びの順に本文へ戻す（数式は `$$ … $$` にする）。TeX が UTF-16 の単位で 1024 を超える数式は画像にせず、コードブロックにする | 窓は今、bot の返答の `TextDisplay` と `Separator` だけを読むので、画像にした数式は窓から消え、次の応答のモデルが前の式を参照できなくなる。画像生成の生成物の説明はプロンプトなので、ファイル名で区別する。component が参照するファイルはメッセージの `attachments` に入らず（Discord の Message Resource の `attachments` の説明）、component の `media` には `attachment_id` と `url` はあるがファイル名の欄は無い。2026-09-28 に、`reasoning.md` を File component で付けた bot の返答を REST で取得すると、`attachments` は空で、`file.url` のパスは `/attachments/<channel>/<attachment_id>/reasoning.md` だった。説明は 1024 字までで、discord.js の検証は UTF-16 の単位（`string.length`）で数える |
| 画像にしない数式 | 描画の失敗、上の大きさや上限を超えるもの、描画の期限に間に合わないもの、SVG に `<text>` 要素を含むもの（内蔵の数式フォントに無い文字を含む。日本語やハングルなど）は、コードブロックで表示する | 数式の中の日本語は、MathJax 3 でも 4 でも正しい字形で描かれなかった（2026-09-27 の試行）。`<text>` の有無で判定すると、文字の種類を列挙せずに、フォントが無いと描けない数式をすべて外せる。ギリシャ文字や数学記号は内蔵のフォントがパスで描くので外れない |
| 文中の数式の表記 | 区切りを外し、中の改行を空白にして、中のバッククォートの連なりより長いバッククォートで囲むインラインコードにする。TeX の先頭か末尾のどちらかがバッククォートなら、囲むバッククォートとの間に、両端とも空白を 1 つずつ入れる | 数式の中にバッククォートや改行があると、単純な `` `…` `` ではインラインコードにならない。端のバッククォートは、空白で離さないと囲むバッククォートとつながって長さが変わる。CommonMark のコードスパンは、中身の両端が空白のときだけ両端の空白を 1 つずつ取り除くので、片端だけに入れた空白は表示に残る |
| モデルへの指示 | 書式の system メッセージ（`DISCORD_FORMAT_SYSTEM_MESSAGE`）に、別行立ての数式は `$$ … $$` か `\[ … \]` で書き、数式の中に日本語を入れず説明は式の外に書くよう足す | 日本語を含む数式は画像にできないので、モデル側で避けさせる |
| 描画の時間と停止 | 1 回の最終描画で、数式の描画に全体で 3 秒の期限を置く。数式を 1 つ描く前に期限を確かめ、過ぎていれば残りの数式をコードブロックにする。1 式の処理は、TeX を UTF-16 の単位で 1024 まで（上の「画像の説明と読み戻し」）に限り、TeX の入力の処理の上限（`maxMacros` と `maxBuffer`）を既定より小さくし、resvg では描く前に大きさを確かめることで抑える。ただし MathJax の変換の計算と resvg の描画は途中で止められず（`handleRetriesFor` もフォントのデータの読み込みを待つだけで、計算自体は止められない）、1 式の時間に厳密な上限は無い。最終描画は、最終の本文を確定したら `updater.markFinalized()` を呼び、その後に分割、数式の描画、送信と編集の順で行う。描画は生成が終わった後に行うので、描画中に停止ボタンが押されたときは、生成が終わった後の今の扱い（「既に完了している」旨を返す）と同じにする | 生成が終わると、停止の対象は外れるが、停止ボタンは最終描画の編集まで表示されている。描画の時間を短く抑え、ボタンが効かない時間を長くしない。ストリーミングの更新は、待ちが打ち切られた後にも遅れて Discord を編集しうる（`toolLoop.ts` の `IToolLoopUpdater` の契約）。今の最終描画は分割の後、編集の直前に `markFinalized()` を呼ぶ。そのまま分割と編集の間に時間のかかる描画を挟むと、描画の間に遅れた更新が古い本文を書き込むので、描画より前に止める |
| 停止と最終描画の途中の失敗 | 生成中に停止したときの書き直し（`updateStoppedMessages`）と、最終描画の送信か編集が途中で失敗したときの致命的エラーの後始末（`cleanupBotMessagesOnFatalError`）では、数式を描かず、別行立ての数式をすべてコードブロックに、文中の数式をインラインコードにした並びを同じ分割器で分けて書き直す。停止した本文の末尾の、閉じの区切りが無い数式は文章のまま残す（上の「数式の検出」）。書き直しの編集では数式の画像の添付を残さない | どちらも今は生成した本文（`updater.text`）を通常の分割器で分け直すので、そのままでは生の TeX が残り、後始末では編集できたページの数式の画像も消える。停止は利用者が待たずに終わらせる操作で、後始末は失敗の後に行うので、時間のかかる描画と添付の送信を行わない |
| 設定 | 設定の切り替えは作らず、常に有効にする | 費用が掛からず、数式が無い返答には何も起きない |

## Design

### 流れ

1. 最終描画の前に、本文を走査で「文章」と「別行立ての数式」の並びに分ける
2. 文章の中の文中の数式をインラインコードに置き換える
3. 分割器が、並びを受け取り、数式を塊として扱ってページに分ける
4. ページごとに、予算に収まる数式を PNG にし、収まらない数式と画像にしない数式をコードブロックにする
5. planner が、本文の区切りと数式の画像を交互に並べた `Container` を作り、添付と合わせて送信または編集する

### 変更対象ファイル

- 新規: `src/utils/mathSegments.ts` — 数式の範囲の走査、文中の数式の置き換え
- 新規: `src/utils/mathRenderer.ts` — TeX から PNG への描画（MathJax の拡張の設定、`merror` の検出、`data-latex` の除去、CSS の埋め込み、resvg、大きさの確認）
- 修正: `src/utils/chatContainerBuilder.ts` — 分割器で数式とインラインコードを塊として扱う。最終描画の `Container` に、本文の区切りと `MediaGallery` を交互に並べ、空の区切りを置かない。編集の payload は planner の契約に合わせる
- 修正: planner（画像生成の `ResponseLayoutPlanner`）— 本文の位置に紐づく画像を割り付ける
- 修正: `src/bot/events/messageCreate.ts` — 最終描画で数式の画像を作り、添付として送る。停止したときの書き直しと致命的エラーの後始末で、数式をコードブロックとインラインコードにして書き直す
- 修正: `src/utils/discordMessageNormalizer.ts` — bot の返答を読み戻すとき、数式の画像を説明から並びの順に本文へ戻す
- 修正: `src/services/chatService.ts` — 書式の system メッセージに数式の書き方を足す
- 修正: `package.json` / `Dockerfile` — `@mathjax/src`、`@resvg/resvg-js` を足す。resvg はネイティブのバイナリを使う
- 修正: `scripts/preview/fixtures.ts` — 数式を含む返答の見本（`bun run preview` で見た目を確かめる）
