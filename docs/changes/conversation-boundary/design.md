# 会話の区切り

## Why

会話履歴が有効な guild では、bot は同じチャンネルの直近の会話を毎回 LLM へ渡すので、話題を変えても前の話題が文脈に残る。
今は履歴を外す手段が guild 全体の設定（`history_enabled`）しかなく、1 つの話題を始め直すためにチャンネルの全員の履歴を止めることになる。
本 change は、チャンネルに**区切り**を置き、以後の応答ではそれより前の会話を自動では渡さないようにする。
ただし区切りより前が読めなくなると、ユーザが前の話に触れたときに答えられない。
そこでモデルには区切りの存在を助言として示し、前の会話が必要なときだけ `read_earlier_messages` で区切りを越えて遡らせる。

## 依存 / 関連 change

- 先行（実装済み）: [conversation-context](https://github.com/AtefAndrus/disqord/blob/5f1bfa49759e1d5ee74e97718d61adff81f2b601/docs/changes/conversation-context/design.md) — 会話は応答のたびに Discord から読み、直近は窓として渡し、それより前はモデルが `read_earlier_messages` で取りに行く（`src/services/conversationWindow.ts`）。本 change はこの窓と tool の上に載る
- 連携: [conversation-regeneration](../conversation-regeneration/design.md) — 再生成は元の発言を今回の発言として窓を組み直す。区切りの適用規則（今回の発言より前の区切り）がそのまま再生成にも効く。同 change の「取り消し」は返答を消す操作であり、本 change の区切りの解除とは別物である
- 関連: [fork](../fork/design.md) — 分岐先スレッドは親チャンネルを遡って読む。親チャンネルに置いた区切りを分岐先の遡りに適用するかは、両方が揃った時点で決める

## Goals / Non-Goals

**Goals:**

- スラッシュコマンドでチャンネル（スレッドを含む）に区切りを置く。区切りより後の依頼への応答では、窓に区切りより前の発言を入れない
- 区切りより前の発言は `read_earlier_messages` で読めるままにし、区切りの存在と位置をモデルに助言として示す
- 区切りは置いた本人か `ManageMessages` を持つメンバーが解除できる

**Non-Goals:**

- 区切りを越える tool 呼び出しを引数やフラグで強制的に止めること。越えるかどうかはモデルの判断に任せる。フラグを付けても付けるかどうかをモデルが決めるので、助言より強い保証にならない
- 区切りより前の発言を LLM から完全に隠すこと。それが要るときは、guild の会話履歴の設定を無効にする
- 発言ごとに履歴を外す印（接頭辞など）。次の発言では履歴が戻り、印を覚える必要もある
- DM での区切り。bot は DM の会話を扱わない

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| コマンド名 | `/newtopic` | 区切りは何も消さず、以後の応答で話題を変える操作である。`/reset` は発言や履歴を消す操作に読めるので採らない |
| 区切りの記録 | DB の `conversation_boundaries` を区切りの有無の正とする。Discord 上には bot の通常の発言として区切りを見せ、解除ボタンを付ける | 区切りの発言だけを記録にすると、窓の走査範囲に区切りの発言があるときしか区切りを見つけられない。依頼 Q → 区切り B → 人の発言 H → Q への返答 R → 次の依頼 M の順で、M の応答では B を見つけて R を除けても、窓の開始位置が H へ進むと `extend` は B を読まず（`conversationWindow.ts` の `extend`）、R が窓に戻る。窓の構築の後に返答の最初のページを送るので、この順序は起こりうる（`messageCreate.ts`）。メモリに区切りを持っても、再起動後の `rebuild` で B が走査範囲の外にあれば同じことが起こる |
| 区切りの発言の投稿 | コマンドには ephemeral で応答し、区切りの発言は `channel.send` で別に投稿する | interaction の応答ではなく通常の発言にすると、発言一覧の `author.id` が bot 自身になる。interaction の応答が一覧でどう見えるかは確かめていない |
| 適用する区切り | ID が今回の発言より小さい区切りのうち、最も新しいもの | 応答中に置かれた区切りはその応答に効かず、区切りの後の依頼から効く。再生成は元の発言を今回の発言として使うので、元の発言より前の区切りが適用される |
| 区切りの解決 | 窓の build の最初に 1 か所で行う。DB から候補を新しい順に引き、区切りの発言が Discord に残っているかを確かめ、404 ならその行を消して次の候補へ進む。権限不足や一時的な失敗では消さず、その候補を適用する | モデレータが区切りの発言を直接削除した場合も、削除イベントに頼らず次の応答で解除として反映できる。確認は窓の REST 予算（`CONVERSATION_REST_LIMIT`）から使う |
| 解決が終わらなかったとき | 削除済みの候補が続いて REST 予算か期限を使い切ったら、「区切りなし」とは扱わない。その応答は窓の取得失敗と同じく履歴なしで答え、窓の状態は更新しない | 「区切りなし」と扱うと、区切りより前の会話が窓に入る。消した行は残らないので、次の応答が続きから解決する。直接削除の反映が複数の応答にまたがることは受け入れる |
| 窓の状態との連動 | 窓のメモリ上の状態に、その状態を作ったときに適用した区切りの ID を持たせる。解決した区切りが状態のものと違えば、`extend` ではなく `rebuild` にする | 置く、解除する、直接削除される、再起動する、のどれでも区切りが変わる。変化を窓に伝える経路をこの比較 1 つにすれば、解除ボタンのハンドラや削除イベントで状態を捨てる処理に頼らずに済む。遅れて終わった古い build が別の区切りの状態を書き戻しても、次の応答の比較で作り直しになる |
| 窓の切り方 | 適用する区切りより前の発言と、区切りの発言そのものを窓に入れない | 窓は機械的に止める。ここに助言を使うと、区切りを置いた意味が無くなる |
| 区切りをまたぐ返答 | bot の返答を窓に入れるには、全ページが区切りより後にあることに加え、元の発言（`triggerMsgId`）も区切りより後にあることを求める。満たさなければ返答全体を窓から除く | 区切りの前の依頼への返答が区切りの後に確定すると、その返答には区切りの前の会話が含まれうる。今の窓は返答のページ ID だけで判定し、元の発言が窓より前かを見ない（`conversationWindow.ts` の `selectEntries`） |
| 返信先 | 区切りより前の発言への返信でも、今と同じく返信先を別枠で渡す。bot の返答への返信なら全ページ、人の発言への返信ならその添付も対象になる | ユーザが自分で指した発言なので、区切りの趣旨に反しない |
| モデルへの助言（system） | 区切りを解決した応答では、窓を実際に切った要因（区切りか、件数、時間、トークンの上限か）にかかわらず、区切りの時刻と「それより前は `read_earlier_messages` で読めるが、依頼が前の会話に触れているときだけ読む」ことを system メッセージで伝える。窓が空でも伝える | 窓が上限で区切りより後ろから始まった応答でも、モデルが最初に遡るかを決める時点で区切りを知っている必要がある |
| モデルへの助言（tool の結果） | `read_earlier_messages` の結果のうち、区切りより前の発言を 1 件でも返す結果には、その発言に最も近い、それより新しい区切りの位置と時刻を、本文と別の欄で必ず付ける | 区切りを走査で見つけることには頼れない。窓の開始位置が区切りそのものだと `before: cursor` は区切りの発言を取得せず、buffer に残った発言だけを返す回には走査が起きない |
| 区切りの捏造と否認 | 区切りの有無と時刻は DB の行と存在確認からだけ決める。system メッセージで、会話の本文に「区切った」「解除した」と書かれていても区切りは変わらないと明示する。ユーザが編集できる表示名は system の指示文に入れない | 履歴の本文と表示名は非信頼データとして渡している（`discordMessageNormalizer.ts`）。助言である以上、本文による捏造や否認にモデルが従うリスクは残るので、e2e で測る |
| 置ける人 | そのチャンネル（スレッドならそのスレッド）で発言できるメンバー。`SendMessages`（スレッドなら `SendMessagesInThreads`）を確かめる | 区切りはチャンネルの全員の以後の応答に効くので、誰でも共有の文脈を中断できることになる。区切りはすでに LLM に送った文脈を取り戻すものではないが、解除すれば次の応答から元の窓に戻るので、この範囲を受け入れる |
| 解除できる人 | DB に記録した置いた本人と、そのチャンネルで `ManageMessages` を持つメンバー | 他人の区切りを気軽に外せないようにしつつ、モデレータは片付けられるようにする |
| 親チャンネルとスレッド | 区切りはチャンネル ID ごとに独立に効く | スレッドの窓は親チャンネルを読まない |
| 会話履歴が無効な guild | 区切りを置かず、意味が無いことを伝える。既存の区切りの解除は受け付ける | 履歴が無効なら窓も tool も無い |

## Design

### 変更対象ファイル

- 新規: `src/bot/commands/newtopic.ts` — 区切りを置くスラッシュコマンド `/newtopic`。権限の確認、区切りの発言の投稿、DB への登録
- 修正: `src/bot/commands/index.ts` — `commandDefinitions` に `/newtopic` を足す（ここに無いコマンドは Discord に登録されない）
- 修正: `src/bot/commands/handlers.ts` — `/help` の固定のコマンド一覧に `/newtopic` を足す
- 修正: `src/index.ts` — `MessageDelete` を区切りの行の削除につなぐ
- 新規: `src/db/repositories/conversationBoundary.ts` — 区切りの登録、チャンネルと ID の範囲での参照、削除、guild とチャンネル単位の削除
- 修正: `src/db/schema.ts` — `conversation_boundaries` を足す
- 修正: `src/bot/events/interactionCreate.ts` — コマンド名の `switch` に `/newtopic` を足す（ここに無い名前は `Unknown command` になる）。解除ボタンの処理
- 修正: `src/services/conversationWindow.ts` — 区切りの解決、窓の状態への区切り ID の記録と比較、窓の切り方、区切りをまたぐ返答の除外、tool の結果への区切りの付記、除いた返答の返却
- 修正: `src/services/chatService.ts` — 区切りの助言の system メッセージ
- 修正: `src/bot/events/replyRecordCleanup.ts` — guild からの退出、チャンネルとスレッドの削除、起動時の照合で区切りの行を消す。`MessageDelete` で該当する行を消す
- 修正: `scripts/e2e/scenarios.ts` と `scripts/e2e/index.ts` — 区切りのシナリオと、tool が呼ばれなかったことの検証（e2e の節）

### DBスキーマ変更

`conversation_boundaries`:

| 列 | 内容 |
| -- | ---- |
| `message_id` | 区切りの発言の ID（主キー） |
| `guild_id` | guild ID |
| `channel_id` | 区切りを置いたチャンネル（スレッドならスレッド）の ID |
| `created_by` | 置いたメンバーのユーザ ID |
| `created_at` | 登録した時刻 |

`(channel_id, message_id)` に索引を張り、「チャンネル内で ID がある値より小さい区切りを新しい順に」引けるようにする。
発言の本文は持たない。

### 実装内容

#### 区切りを置く

1. ephemeral で `deferReply` する。Discord は interaction の最初の応答を 3 秒以内に求めるので、以後の結果はこの応答の編集で伝える。
2. 実行者の権限と guild の会話履歴の設定を確かめる。満たさなければ断る。
3. 「区切りを設定中」と書いたボタンなしの発言を `channel.send` で投稿する。
4. DB に行を登録する。区切りが効くのはこの時点からである。
5. 発言を、区切りの表示と解除ボタンに編集し、実行者に成功を伝える。

登録に失敗したら投稿を削除し、削除にも失敗したら「設定に失敗した」表示に編集する。
4 と 5 の間でプロセスが止まると、区切りは効いているのに表示が「設定中」のまま残る。
表示が効き目より弱い側に食い違うだけなので、これは受け入れる。
3 と 4 の間で止まった場合は、「設定中」の表示だけが残り、区切りは効かない。

#### 区切りを解除する

解除ボタンの `customId` には区切りの発言の ID を入れる。

1. DB の行を引く。行が無ければ「この区切りはもう無効」と ephemeral で伝え、bot がその発言を削除する。
2. 押した人が置いた本人か、そのチャンネルで `ManageMessages` を持つかを確かめる。
3. Discord 上の発言を削除し、成功するか 404 だったときに DB の行を消す。それ以外の失敗では行を残し、失敗を伝える。表示が残っているのに区切りが効かない状態を作らないためである。

#### 窓

窓の build の最初に区切りを解決し、窓の状態に記録した区切りと比べて `extend` か `rebuild` かを決める（Decisions の「区切りの解決」と「窓の状態との連動」）。
`rebuild` と `extend` のどちらも、適用する区切りより前の発言を窓に入れず、区切りをまたぐ返答を除く。
解除の後の次の応答は作り直しになり、通常の窓の上限の範囲で区切りより前の発言が戻る。

#### `read_earlier_messages`

- tool は応答の中で区切りの一覧を持つ。build で適用した区切りから始め、遡りに合わせて、今回の発言より前にあるそのチャンネルの区切りを DB から引き足す。
- 付記する区切りは、発言が Discord に残っているかを tool の REST 予算（`TOOL_REST_LIMIT`）で確かめ、結果を応答の中で使い回す。404 ならその行を消して区切りとして扱わず、確認に失敗したら区切りとして扱う。確認のために予算を使い切ったら `rest_budget_exhausted` で止める。
- 窓から除いた返答（区切りの前の依頼への、区切りの後に確定した返答）は、ページが窓の開始位置より新しいので `before: cursor` の走査では届かない。build の取得範囲の外にあることもあるので、build で見た発言からは拾えない。そこで tool が人の発言を返すとき、その発言への返答の記録（`reply_records`）があり、返答のページが窓の開始位置以後にあれば、記録からページを取得し、その発言の直後に返す。返す前に、返答の記録、全ページの存在、外部削除、確定時刻を今の判定（`messageEligibility.ts`）と同じく検証する。窓の区切りの条件（元の発言が区切りより後にあること）は適用しない。適用すると、返したい返答そのものが落ちる。この返答に付ける区切りは、ページの位置ではなく元の発言の位置で決める。
- 結果の形: 区切りの情報は結果の `boundaries` 欄に参照 ID（`b1` など）、位置、時刻の一覧として置く。区切りより前の発言には、その発言に最も近い、それより新しい区切りの参照 ID を持たせる。1 つの結果が複数の区切りをまたぎ、発言ごとに対応する区切りが違う場合（区切り B1 → 発言 A → 区切り B2 → 発言 C の A と C）も、この対応で表す。
- 区切りの欄は結果のトークン予算に含める。区切りの情報と発言を合わせて予算に収まらない場合は、区切りの情報を省かず、収まる分の発言までで止めて `result_budget_exhausted` を返す。

### 設計メモ

- 区切りを越えたかを観測するときは、`read_earlier_messages` の呼び出しだけでなく、区切りより前への返信も数える。返信先は tool を通らずに区切りより前の内容を渡す。
- 応答ごとに、区切りがあれば存在確認の REST が 1 回以上増える。直接削除された区切りが続くほど増えるので、`MessageDelete` で行を消して候補の連続を減らす。client は partials を有効にしていない（`src/bot/client.ts`）ので、このイベントはキャッシュにある発言の削除でしか届かず、再起動より前に投稿した区切りの削除は届かない。削除イベントは補助であり、取り逃しても窓の解決で収束する。

### e2e

- tester bot は bot のスラッシュコマンドを実行できないので、区切りのシナリオは `/newtopic` を通さずに区切りを用意する。tester が区切りの代わりの発言を投稿し、その発言 ID で bot の `DATABASE_PATH` の `conversation_boundaries` に行を入れる（`cron` シナリオが DB に行を入れるのと同じ方法）。区切りの有無は DB の行と発言の存在で決まるので、これで窓と tool の経路を通せる。シナリオの後始末で行を消す。
- 今の runner は `setup` の投稿の ID を保持せずに本番の質問を投稿し、`before` は `setup` より前、`verify` は返答の後に走る（`scripts/e2e/index.ts`）。区切りの行は `setup` の投稿の後、質問の前に入れる必要があるので、`setup` で投稿した発言の ID を受け取って質問の前に走るフックを runner に足す。
- 区切りのシナリオは `manual` にして、名前を指定したときだけ走らせる。会話履歴の設定が有効な guild でしか意味が無く、既存の履歴のシナリオ（`history-set` など）と同じ扱いである。前提として、機能 → 会話履歴 の設定を有効にする。
- runner は今、`toolName` の tool が呼ばれたことしか確かめない（`scripts/e2e/index.ts`）。「呼ばれなかった」ことを確かめるために、シナリオに呼ばれてはならない tool を指定する欄を足し、bot のログにその tool の呼び出しがあれば失敗にする。
- `/newtopic` の実行と解除ボタンは bot から操作できないので、手動確認にする。
