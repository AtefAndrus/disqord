# 検索結果リンクを検索ごとに交互に選ぶ

## Why

回答の下の `-# 検索結果` は、全検索の結果を受け取った順に並べ、先頭の `MAX_RESULT_LINKS`（5 件）で打ち切っている（`src/llm/tools/webSearch.ts:77`、`:130`）。
1 回の検索は最大 `RESULTS_PER_SEARCH`（5 件）の結果を返すので（`src/llm/tools/webSearch.ts:15`）、1 本目の検索が表示できる重複の無い結果を 5 件返すと、検索が 2 回以上あっても表示されるのは 1 本目の検索の結果だけになる。
2026-10-25 に本番で 2 回検索した回答が 2 件あり、どちらも 1 本目の検索の 5 件だけが表示され、2 本目の結果は 1 件も出なかった（`Web search` のログ行の `sources` と表示されたリンクを突き合わせて確認した）。
裁判例を挙げた回答では、2 本目の検索が返した裁判所の判例 PDF が表示されなかった。
1 本目で URL に含まれるアカウント名と投稿 ID を検索した回答では、表示された 5 件が Minecraft サーバーの状態確認や WHOIS のページになった。

## Goals / Non-Goals

**Goals:**

- 検索が複数あるとき、表示できる結果を持つ検索の先頭 5 本は、それぞれ少なくとも 1 件が表示される。表示できる結果とは、今の無害化の条件を通り、それより前の検索の結果と重複せず、その検索の `sources` と対応付けられた結果である。
- 表示できる結果を持つ検索が 1 本以下の回答は、今と同じリンクを同じ順に表示する。
- 表示件数の上限 5 件、タイトルと URL の無害化、重複の除去は変えない。

**Non-Goals:**

- モデルが本文で使った結果を優先すること。OpenRouter の `url_citation` は、モデルに渡した結果ごとに 1 つ付き、`start_index` と `end_index` が 0 のままなので（`src/types/index.ts:337-341`）、本文のどこで使ったかが分からない。
- 的外れな検索の結果を表示から外すこと。結果が質問に合っているかを bot の側では判定できない。
- 検索語を表示すること。

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| 選び方 | 検索ごとに結果を分け、検索の順に 1 件ずつ交互に取り、上限 5 件に達するまで繰り返す。検索 2 回なら 1 本目から 3 件、2 本目から 2 件になる | 上限と表示の形を変えずに偏りだけを取り除ける。1 本目が的外れでも、他の検索の結果が表示に入る |
| 結果と検索の対応 | 結果（`url_citation`）の URL と、各検索の `sources`（`WebSearchCall.sources`、`src/types/index.ts:330-334`）の URL を、どちらも `new URL().href` に正規化して突き合わせ、最初に一致した検索の結果とする。`new URL()` が解析できない `sources` の要素は無視する | 結果の側には、どの検索から来たかの情報が無い。`sources` は文字列であることしか確認せずに受け取っているので（`src/llm/openrouter.ts:167-171`）、解析できない値で表示全体が失敗しないようにする |
| どの検索にも一致しない結果 | 交互に選んだ後に残った枠を、一致しない結果で元の順に埋める | `sources` を返さない呼び出し（`max_uses` を超えて断られた検索、`src/types/index.ts:332`）や、URL の表記がずれるエンジンがあっても、結果が表示から消えないようにする。一致した結果を先に並べるのは、どの検索から来たか分かる結果で各検索を代表させるためである |
| 表示できる結果を持つ検索が 1 本以下のとき | 交互に選ばず、今と同じく結果を元の順に並べて先頭 5 件を取る | 交互に選ぶ目的は検索の間の偏りを取り除くことで、検索が 1 本ならその目的が無い。一致しない結果を後ろに回すと、検索 1 回の回答でも表示が変わってしまう |
| 検索の数 | 回答全体の検索の数に上限を置かない。6 本以上あると、交互に選ぶ 1 巡目で枠が尽き、6 本目以降の結果は表示されない | `MAX_SEARCHES`（4）は 1 リクエストあたりの上限で（`src/llm/tools/webSearch.ts:28-32`）、tool loop は複数ターンの検索を連結する（`src/llm/toolLoop.ts:1323-1326`）。Anthropic 以外の native 検索にはこの上限が効かない（`describeSearchBilling()`）。上限 5 件を変えない以上、検索が多いときに先の検索を優先するのは今と同じである |
| 却下: 検索語ごとに見出しを付けて分ける | 採らない | 外れたリンクがどの検索から来たかは分かるが、見出しの分だけフッターが長くなり、モデルが書いた検索語を Discord に出すための無害化が新たに要る |
| 却下: 上限を増やす | 採らない | 上限を上げれば後の検索の結果も表示に入るが、1 本目の結果から先に並ぶ偏りは残り、検索 1 本あたり最大 5 件ずつリンクの列が最終ページで本文の後ろに長くなる |
| 関数の引数 | `formatSearchResultLinks()` は `WebSearchResultLink[]` の代わりに `WebSearchTrace`（`calls` と `results`）を受け取る | 呼び出し元の 2 か所（`src/bot/events/messageCreate.ts:646`、`src/services/cronService.ts:725`）は、どちらもすでに `WebSearchTrace` を持っている |

## Design

### 変更対象ファイル

- 修正: `src/llm/tools/webSearch.ts` — `formatSearchResultLinks()` の引数を `WebSearchTrace` にし、無害化と重複の除去を通った結果を検索ごとに分けて交互に選ぶ。
- 修正: `src/bot/events/messageCreate.ts`、`src/services/cronService.ts` — 呼び出しに `webSearch` 全体を渡す。
- 修正: `tests/unit/llm/webSearch.test.ts` — 既存のテストを新しい引数に合わせ、交互に選ぶテストを足す。

### 実装内容

1. 各検索の `sources` を、`new URL().href` に正規化した URL の集合にする。解析できない要素は飛ばす。
2. 結果を順に見て、今と同じ条件（http(s) のみ、`MAX_URL_CHARS` 以下、空白と `<>` を含まない、ホスト名の文字種、重複の除去）を通ったものを、最初に一致した検索のグループに入れる。一致しないものは「一致なし」の列に入れる。
3. 結果を持つ検索のグループが 1 つ以下なら、条件を通った結果を元の順に並べ、先頭から `MAX_RESULT_LINKS` 件を取る。
4. グループが 2 つ以上なら、グループを検索の順に巡って 1 件ずつ取り、空になったグループは飛ばす。合計が `MAX_RESULT_LINKS` に達するか、すべてのグループが空になったら止め、枠が残っていれば「一致なし」の列から元の順に埋める。

## Open Questions / Risks

- Perplexity 以外のエンジン（`native`、`exa` など）で、`sources` の URL と `url_citation` の URL が同じ表記になるかは未確認である。すべて一致しない場合は、結果を持つ検索のグループが 1 つ以下になり、今と同じ表示に戻る。
一部だけ一致しない場合は、一致したグループが 2 つ以上残れば交互に選ぶほうが働き、一致しない結果は残りの枠にしか入らないので、今は先頭 5 件に入る結果が表示から外れることがある。
