# 自動応答で返答するかを判断する

## Why

自動応答チャンネルでは、bot はすべての発言に返答する。
人どうしの雑談や相づちにも返答するので、会話に割り込み、読む側にも費用にも無駄が出る。
返答するかどうかを発言ごとに判断し、口を挟む場面でなければ黙るようにする。

## 依存 / 関連 change

- 前提（実装済み）: [conversation-context](https://github.com/AtefAndrus/disqord/blob/5f1bfa49759e1d5ee74e97718d61adff81f2b601/docs/changes/conversation-context/design.md) — 会話の窓。判定は返答のために作る窓を流用する
- 連携: [settings-hierarchy](../settings-hierarchy/design.md) — 判定の有無やしきい値をチャンネル単位で変えたくなったら、同 change の設定の階層に載せる

## Goals / Non-Goals

**Goals:**

- 自動応答チャンネル（とその中のスレッド）の、bot へのメンションが無い発言について、返答する前に返答すべきかを判定する
- 返答しないと判定したら、エラー表示を含めてチャンネルに何も送らない
- guild ごとに on/off を切り替えられ、既定は off にする
- 判定の結果を、後でしきい値を調整できる形でログに残す

**Non-Goals:**

- メンションされた発言の判定。メンションは明示的な呼び出しなので、今までどおり必ず返答する
- 自動応答でない通常のチャンネルで、呼ばれていない発言に自発的に返答すること
- 運用前の評価データを作ってしきい値を詰めること。初期のしきい値で出し、運用のログがたまってから調整する

**将来別 change 候補:**

- しきい値の再調整: ログの ID から会話を取り直してラベルを付け、しきい値ごとの正解率を出すスクリプトを作り、しきい値を決め直す。他の判定モデル（下の「判定モデルの選定」の候補）との比較もこのとき同じラベルで行う

## Decisions

| 判断事項 | 選択 | 理由 |
| -------- | ---- | ---- |
| 方式 | 返答の生成より前に 1 回だけ判定し、返答すると判定したときだけ「生成中...」を送って生成に進む | 黙るときは画面に何も出ない。本番のモデルに「黙る」出力を持たせる方式は、「生成中...」を先に出すと表示が出て消え、出さずに待つと返答するときの表示が最初の文字まで遅れる |
| 判定のモデル | TypeSafe の判定モデル Jev（`typesafe/jev-1.14`）の `noul`（はいの確率を返す質問）を、OpenRouter の Decisions API（`POST /api/alpha/decisions`）で呼ぶ。版は `~typesafe/jev-latest` にせず固定する | 判定モデルは文章を生成せず確率を返すので、しきい値で黙りやすさを調整できる。チャットモデルに真偽を出力させる方式は確率が得られず、2026-09-27 の試行では `openai/gpt-6-luna` で中央値 423ms、`deepseek/deepseek-v4.1-flash` で最大 2.9 秒かかった。判定モデルの中で Jev を選ぶ理由は下の「判定モデルの選定」に置く。版を固定するのは、版が変わると確率の分布が変わり、しきい値の意味がずれるためである |
| しきい値 | 環境変数 `REPLY_GATE_THRESHOLD`（既定 0.3）以上なら返答する | 返答すべき発言を黙って落とす誤りは、黙るべき発言に返答する誤り（判定を入れる前と同じ挙動）より不満が大きいので、返答する側に寄せる。本番は 1 回の判定で決めるので、1 回ごとの値で見る。「判定モデルの選定」の 77 件を本番と同じ `state` の形で 3 回ずつ判定させると（2026-10-18）、返答すべき例の判定 114 回の確率は最小 0.35 で、0.3 を下回った回は無かった。黙るべき例の判定 117 回のうち 16 回が 0.3 以上だった。同じ例でも実行ごとに確率が最大 0.08 揺れる。例が手書きで作為的なので、運用のログで決め直す |
| OpenRouter の Auto Router | 使わない | 判定のモデルを選ぶ用途ではない。`openrouter/auto` は呼ぶたびに別のモデルを選び、推論のトークンも付いて、2026-09-27 の試行で 0.8〜2.9 秒かかった |
| 判定の失敗 | 時間切れ（3 秒）、エラー、応答の形の誤り（`noul` が 0〜1 の数でない）のどれでも返答する | 判定を入れる前の挙動（必ず返答する）に倒す。Decisions API はパスが `alpha` で、予告なく変わりうる |
| 判定の入力 | Jev の `state` に、bot の名前、会話の窓の新しい方から最大 20 件、新しい発言を入れる。新しい発言が返信なら、返信先（窓の `replyTarget`）も別の項目に入れる。返信先は 20 件に数えず、合計 3,000 トークンの上限には数える。1 件は 400 字までにする。発言の添付は、種類とファイル名だけを文字で書く（例 `[画像 photo.png]`）。各発言は「名前: 本文」の形にし、bot の返答の名前は bot の名前、bot へのメンションは `@<bot の名前>`、人へのメンションは `@メンバー` に書き換える。新しい発言の名前は、窓の過去の発言と同じく表示名かユーザ名にし、ニックネームを使わない。会話履歴が off なら、窓の代わりに新しい発言が bot の返答への返信かどうかだけを入れる | 返答するかは直近のやり取り（誰に向けた発言か、bot の直前の返答への続きか、人どうしの会話が続いているか）でほぼ決まる。問いは bot を名前で指すので、窓が bot の返答に付ける名前（`assistant`）や生のメンション（`<@id>`）のままでは、bot への続きの発言や人宛ての発言だと読み取れない。人へのメンションを ID のまま渡すと、Jev は「`<@id>` この英文訳せる？」を bot 宛てと判定した（確率 0.73、`@メンバー` に書き換えると 0.50）。人の名前を引かないのは、窓がメンバーの情報を持たず、メンションごとに取得すると判定が遅れるためである。新しい発言だけニックネームを使うと、同じ人の発言が別人として渡る。窓は返答のためにどのみち作るので、追加の取得は要らない。添付の中身は渡さない。Jev 1.14 は画像を読めるが、画像を含むリクエストはすべて TypeSafe の長文脈モードで処理され、文書によれば遅く精度も下がる。履歴が off の guild は会話を渡さない選択をしているので、判定にも渡さない |
| 判定の問い | `noul` の指示と基準は下の「判定の問い」に置く。文面は運用のログで調整する | 試行で使った文面を出発点にする |
| 判定より前のエラー表示 | 判定の対象の発言では、添付の拒否、画像非対応のモデル、本文も添付も無い発言へのエラー表示を判定より後に回す。本文も添付も無い発言（スタンプだけなど）は判定せずに黙る。返答すると判定したときだけ、今までのエラー表示を出す | 今はこれらのエラーを窓を作る前に返信するので、判定を入れても、自動応答で呼ばれていない発言に bot がエラーで割り込む |
| 無料モデル限定の guild | 判定を行わず、今までどおり返答する。設定パネルの項目の説明にそう書く | Jev は有料である（入力 1M トークンあたり $0.042）。無料モデル限定は「無料モデルだけを利用する」という設定なので、判定だけ有料で呼ぶと設定の意味と食い違う。無料の判定モデル `inception/mercury-decide:free` は、OpenRouter のアカウント設定で無料モデルによる学習を許さないと呼べず（2026-10-17 に 404 で確認）、会話を渡す判定には使わない |
| ログ | 判定のたびに、`noul` の値、判定の結果、しきい値、guild・チャンネル・メッセージの ID、時間、費用を記録する。発言や会話の本文は記録しない | 再調整では ID から会話を Discord で取り直してラベルを付ける。ログは本番でファイルに残り、管理 API から読めるので、本文を新たに持たない。削除された発言は取り直せないが、利用者が消したものなので取り直さなくてよい |
| 黙ったときの返答記録 | 作りかけの返答記録（`reply_records` の `pending`）を消し、その発言を返答の無い人の発言として扱う。同じ発言のイベントが二重に届いたときに判定し直さないよう、黙った発言の ID をメモリに 1 時間持ち、届いた発言がその中にあれば何もしない | 返答記録の状態に「返答しなかった」を足すと、SQLite の CHECK 制約の変更に表の作り直しが要る。記録が無ければ、窓は今でもその発言を返答の無い発言として扱う。Discord はイベントを複数回届けることがあり、記録を消すと既存の重複の防止（`createPending()` が既存の記録を見て終える）が効かず、しきい値付近では 2 回目の判定で返答しうる。二重の配信は接続の再開の直後に起きるので、メモリに短い時間持てば足りる。discord.js は gateway のセッションをプロセスの外に保存しないので、再起動の後は新しいセッションになり、古いイベントは届き直さない |
| 設定 | 設定パネルの「応答」ページに「自動応答の取捨選択」の on/off を足し、`guild_settings` の列 `reply_gate_enabled`（既定 0）に保存する | 既存の自動応答チャンネルの挙動を、管理者の明示なしに変えない |

## Design

### 判定の問い

```json
{
  "type": "noul",
  "instructions": "Discord のチャンネルに常駐する AI アシスタント「<bot の名前>」が、新しい発言に返答すべきかを判定する。",
  "criteria": {
    "true": "<bot の名前> に向けた発言（名前で呼ぶ、<bot の名前> の直前の回答への続きの質問）、または参加者が答えや作業を求めていて <bot の名前> が役に立つ発言。",
    "false": "人どうしで続いている会話、相づちや感想、特定の人に向けた発言、<bot の名前> の回答への礼や人どうしの反応。"
  }
}
```

### 判定モデルの選定

2026-10-17 時点で、Decisions API で使える判定モデルは 27 個ある（[一覧](https://openrouter.ai/models?output_modalities=decisions)）。
上の「判定の問い」で、手書きの 77 件（返答すべき 38 件、黙るべき 39 件）を各モデルに 2 回ずつ判定させた（2026-10-17）。
下の表の値は、人へのメンションを名前で書き、返信先を窓の発言にも重ねて入れた簡略な `state` で測ったものである。本番と同じ形での Jev 1.14 の値は Decisions の「しきい値」の行にある。
例は `scripts/reply-gate-cases.ts` にあり、`bun scripts/reply-gate-eval.ts <model>...` で同じ比較をやり直せる。
77 件には、話題は bot 向きだが特定の人に宛てた質問、人にしか答えられない「誰か」宛ての質問、bot への礼に続く質問、bot の名前を出すだけの雑談のように、表面の手がかりと正解が逆を指す 30 件を含めた。
AUC は、返答すべき例が黙るべき例より高い確率を得た組の割合である。
ずれは、同じ例を 2 回判定したときの確率の差の最大である。
時間は開発機から全モデルへ並行して送ったときの値で、本番のホストからの値ではない。

| モデル | AUC | ずれ | 時間の中央値 / p90 | 1 回の費用 | 備考 |
| - | - | - | - | - | - |
| `typesafe/jev-1.14` | 0.998 | 0.05 | 326 / 382ms | $0.000023 | |
| `typesafe/jev-1.13` | 0.996 | 0.06 | 324 / 382ms | $0.000023 | |
| `liquid/d1-ultra` | 1.000 | 0.12 | 450 / 542ms | $0.000009 | |
| `perplexity/pplx-decider-v1.2` | 0.999 | 0.00 | 520 / 575ms | $0.000005 | 154 回中 25 回が 429 を返し、再送が要った |
| `nace-ai/drex-v2.0` | 0.995 | 0.00 | 590 / 890ms | $0.000011 | |
| `liquid/d1` | 0.995 | 0.15 | 496 / 790ms | $0.000005 | |
| `microsoft/microsoft-decision-1` | 0.990 | 0.09 | 424 / 507ms | $0.000008 | |
| `inception/mercury-decide` | 0.988 | 0.38 | 744 / 1,052ms | $0.000004 | |
| `openai/gpt-6-luna-decisions` | 0.967 | 0.00 | 404 / 512ms | $0.000036 | |

上位 5 モデルの AUC の差は、順序を取り違えた組が 0〜3 組あるかの差で、この件数では優劣を示さない。
そのため、判定が返答の前に必ず挟まることから時間を重く見て、上位で最も速い Jev を選ぶ。
同じ条件で、Jev は 2 回の判定のずれが 0.05 と小さく、しきい値付近の発言の判定が呼ぶたびに入れ替わりにくい（`liquid/d1-ultra` と `liquid/d1` は 0.12〜0.15 ずれた）。
1.13 と 1.14 に差は無く、新しい 1.14 に固定する。
費用は表のどのモデルでも 1 回 $0.00004 未満で、選定に効かない。
Jev は同じ文を表の多くのモデルの約 2 倍のトークンに数えるので、1M トークンあたりの単価だけで費用を比べると見誤る。

表のほかに、次のモデルを候補から外した。
`upstage/solar-decide`、`upstage/solar-decide-flash`、`togethercomputer/tev1-4b-experimental` は、表面の手がかりと正解が逆を指す 30 件を除いた 47 件で測った。

- `respan/span-01` 系と `scaledown/classify-1`: 独自の `state` の形しか受け付けず、400 を返す
- `upstage/solar-decide`: 時間の中央値が 6.4 秒で、同じ例の確率が最大 0.88 ずれた
- `upstage/solar-decide-flash`、`togethercomputer/tev1-4b-experimental`: AUC が 0.73、0.975 で、しきい値 0.5 での正解率が 0.60、0.79 だった
- `cloudflare/clef-flash`: `state` の先頭約 2,000 トークンしか読まず、残りを黙って捨てる（[Multimodal Decisions](https://openrouter.ai/docs/guides/community/multimodal-decisions) の Limits）。判定の入力の上限 3,000 トークンに足りない
- `cloudflare/clef`、`cloudflare/clef-omni`、`jaredpalmer/kev-4b`、`nace-ai/drex-v1.5`、`perplexity/pplx-decider-flash-v1.2`: AUC が 0.95〜0.98 で上位に届かない

### 変更対象ファイル

- 新規: `src/services/replyGateService.ts` — `state` の組み立て、Decisions API の呼び出し、時間切れと失敗の扱い、ログ
- 修正: `src/llm/openrouter.ts` — Decisions API を呼ぶ関数を足す（リクエストとレスポンスの型を含む）
- 修正: `src/bot/events/messageCreate.ts` — 自動応答の発言で設定が on かつ無料モデル限定でないとき、窓を作った後、「生成中...」を送る前に判定を呼ぶ。添付と入力のエラー表示を判定より後に回す。黙るなら作りかけの返答記録を消して終える
- 修正: `src/services/replyRecordService.ts` / 返答記録の repository — ページの無い `pending` の記録を消す関数
- 修正: `src/config/envVars.ts` — `REPLY_GATE_THRESHOLD`
- 修正: `src/db/schema.ts` / `src/db/repositories/guildSettings.ts` / `src/services/settingsService.ts` / `src/utils/configPanel.ts` / `src/utils/statusMessage.ts` — 設定の列、setter、設定パネルの項目、`/status` の表示
- テスト: `state` の組み立て（件数とトークンの上限、返信先の扱い、添付の書き方、履歴 off）、黙った発言のイベントが二重に届いても判定し直さないこと、しきい値の境界、失敗時に返答すること、メンションと無料モデル限定では判定しないこと、黙ったときにエラー表示を含めて何も送らず記録を消すこと、返答するときは今までのエラー表示を出すこと、ログに本文が入らないこと

### e2e

e2e のテスト bot は、メンションを付けた発言にしか返答されない（2 つの開発用の bot が互いに自動応答し続けるのを防ぐため）。
そのため、メンションの無い発言の判定は e2e では確かめられない。
判定の入力と分岐は単体テストで、実際の挙動は手動確認で確かめる。

## Open Questions / Risks

- **しきい値の妥当性**: 初期値 0.3 は、手書きの 77 件の試行から決めた仮の値である。運用のログがたまったら、将来別 change 候補の再調整で決め直す。
- **判定中の発言と直後の発言**: 判定の間、発言の返答記録は `pending` なので、その間に届いた次の発言の窓から外れる（生成中の発言を窓から外すのと同じ規則）。直前の 1 行を欠いたまま判定することがあるが、判定は通常 0.3 秒ほどで終わり、そこまで短い間隔で続く発言は少ない。
- **Decisions API の変更**: パスが `alpha` なので、仕様が予告なく変わりうる。変わっても判定が失敗して返答するだけで、黙って落とすことはない。
- **履歴 off の判定の弱さ**: 新しい発言だけでは、人どうしの会話の続きかを判断しにくい。履歴 off の guild では、黙るべき発言に返答する側に誤りやすい。
- **添付の中身**: 画像や PDF の中身は判定に渡さないので、本文の無い添付だけの発言は、ファイルの種類と名前と前後の会話で判定する。
