### Documentation policy

| [CHANGELOG.md](CHANGELOG.md) | Change history | Auto-generated by git-cliff. Refresh with `bun run changelog` at release time |

### Update rules

#### progress.md (backlog index) **[auto-generated]**

- The backlog table is generated from the YAML frontmatter of `docs/changes/*/design.md`.
- **Do not edit by hand.** Edit the frontmatter and it is applied automatically at commit time.
- "Backlog" means the active/unreleased change folders (not only unstarted work — implemented-but-unreleased changes are included too).

#### docs/changes/ (per-feature design docs)

- **When considering a new feature**: copy `TEMPLATE.md` to `docs/changes/<feature-name>/design.md`.
  - Folder name is kebab-case English (e.g. `web-search`, `model-compare`). The design.md title heading is written as the Japanese feature name.
  - The YAML frontmatter is required at the top:

    ```yaml
    ---
    title: "日本語の機能名"
    status: investigating  # investigating | planned | in-progress | implemented
    priority: high         # high | medium | low
    summary: "一行の概要"  # optional
    ---
    ```

  - Status transitions:
    - **Plan being formulated** (design still under discussion): start at `status: investigating`.
    - **Plan finalized, not yet started**: `status: planned`.
    - **Implementation started**: `status: in-progress`.
    - **Implementation complete (after merge to main)**: `status: implemented`.
    - **At release**: delete the changes folder (it disappears from progress.md automatically; CHANGELOG.md carries the history).
  - Required sections: Why / Goals・Non-Goals / Decisions / Design / Tasks.
  - Optional sections: "依存 / 関連 change", "Open Questions / Risks", "参照" (delete the whole section if unused). The cross-reference heading must be the Japanese 参照 (do not use "References").
  - The detailed design may be filled in incrementally (it need not be complete at once).
- **Change granularity (folder vs file)**: split by **release unit**, not document size.
  - Features released separately → separate folders (separate changes). The folder is the unit of backlog item, release, and deletion.
  - Multiple sub-features released together (small–medium) → one folder, single `design.md`, with the Design section split into per-feature subsections by `---`.
  - Multiple sub-features released together (large, with a shared core) → one folder, multiple files. Make `design.md` the index (shared Why/Decisions/dependencies + links) and split sub-features into `design.<subfeature>.md`. The folder is indivisible as a release unit (other changes link to `design.md` for link stability).
  - If you later want to release a sub-feature separately, split by folder (a new change), not by file.
- **At release**: delete the changes folder (note the deletion as the final Tasks item). Git history is the archive, so no separate backup is needed.

## Tech Stack

- Runtime: Bun 1.3+
- Language: TypeScript (ESNext, strict mode)
- Framework: discord.js v14
- LLM API: OpenRouter
- Database: SQLite (Bun built-in)
- Linter/Formatter: Biome

## Coding Conventions

### TypeScript

- Use `import type` for type-only imports
- Add explicit return types to functions
- Avoid `any`, define proper types
- Prefix interfaces with `I` (e.g., `ILLMClient`)

### Biome

- Indentation: 2 spaces
- Line width: 100 characters
- Auto-organize imports

### Architecture Patterns

- Repository pattern for data access
- Service pattern for business logic
- Constructor injection for DI

### Naming

- Files: camelCase (e.g., `chatService.ts`)
- Classes: PascalCase (e.g., `ChatService`)
- Interfaces: `I` + PascalCase (e.g., `IChatService`)
- Constants: UPPER_SNAKE_CASE

## Testing

- Framework: bun:test
- Directory: `tests/`
- Run: `bun test` (includes typecheck)

### Mock Strategy

| Dependency | Mocking approach |
| ---------- | ---------------- |
| `fetch` | Replace globally with `mock()` |
| `bun:sqlite` | In-memory DB (`:memory:`) |
| Repository/Service | Implement the interface with `mock()` |
| `console.*` | Verify output with `spyOn()` |

## Release Process

Use the `/release` skill to automate the release process. Example: `/release 1.5.0`

The skill handles: version bump, CHANGELOG.md generation, deleting the changes folder (auto-reflected in progress.md), commit, tag, push, and GitHub release creation with hand-crafted release notes.

### Release Notes Guidelines

- Release notes are delivered to Discord users via webhook.
- Only include user-facing changes (new features, bug fixes, UX improvements).
- Do NOT include internal technical changes (test fixes, refactoring, code cleanup).
- Write the notes in Japanese with detailed feature descriptions (see existing releases for style reference).
- End with: `**Full Changelog**: https://github.com/AtefAndrus/disqord/compare/v{previous}...v{current}`
